# 重要支出年度总览与虚拟订阅关联

**状态：A–D 全部阶段已实现，独立 Review 的 R1–R7 已修复并完成回归及隔离原生核心验收；本地主分支合并采用 schema 33，尚未发布。** 本文是主规格；已实现行为的现行口径同步见[产品规则](PRODUCT_RULES.md)与[使用指南](USER_GUIDE.md)，原生验收边界见[开发说明](DEVELOPMENT.md)。

## 1. 目标、现状与范围

重要支出适合先回顾多年投入，再进入某年查看月份。目前普通进入默认选今年，“全部”已汇总各年金额和明细，但没有年度图表。目标是默认全部、展示逐年柱状图、点击年份进入月度图。

虚拟资产保存服务与权益档案，周期计划保存计费与付款事实。目前新建订阅可在一次事务中创建两者，费用也没有重复计算，但删除任一对象不会带走另一方，两个入口的编辑与状态展示也不同。目标是已关联记录作为一组管理，共用计费信息、付款事实与生命周期。

| 本次包含 | 保持边界 |
|---|---|
| 重要支出默认期间、年度聚合、年度图与年份钻取 | 不扩展为日常流水，不新增消费归因或预算功能 |
| 已关联虚拟档案与计划的详情、计费编辑、删除恢复 | 保留两个模块与现有一级导航 |
| 独立订阅计划明确建立服务档案 | 不给房租、保险等强制建虚拟资产 |
| 历史关联不完整的核对与兼容 | 不按名称合并，不自动补造付款或改历史金额 |

单次购买、储值、独立周期费用继续采用各自业务规则。已有关联的旧域名等档案也适用关联生命周期保护，但原计费、有效期和排期语义保持；不能因新版界面统一而改成现代月订阅。

## 2. 重要支出的入口与页面结构

### 2.1 期间选择

| 入口／操作 | 所选期间 |
|---|---|
| 首次或重新从侧栏普通进入 | 全部 |
| 总览某年重要支出指标进入 | 明确传入的年份 |
| 支出来源跳转 | 原记录所属年份；日期未知时为全部 |
| 点年度柱或年份按钮 | 对应年份 |
| 点“全部” | 全部 |
| 从当前明细打开原记录后返回 | 保存的期间、搜索与滚动位置 |
| 切换资料库 | 清除旧返回上下文，普通进入从全部开始 |

区分普通入口与带上下文的返回，不能只靠页面重新挂载判断。期间变更不保存到数据库或跨资料库偏好。跨年时补上新今年按钮，不擅自改变用户已选期间。

### 2.2 页面排列

从上到下保持：期间控件 → 支出／退款／净支出／售出回收四项摘要 → 日期或金额待补提示 → 期间图表 → 明细。顶部信息提示说明“仅已记录支出；退款按发生日期；售出回收单列；搜索只筛选明细”。

全部时图表标题为“各年支出”，横轴为年份，按时间升序；单年时标题为“各月支出”，横轴固定 1–12 月。年份控件按现有方式从新到旧排列，始终有“全部”和今年，即使今年没有记录。

年度柱只为有带日期来源记录的年份建立，不填造缺记录的中间年份。间隔年份按真实年份标识，图表注明“仅列有记录的年份”。十年以上数据不截断，窄窗允许图表区横向滚动；页面本身不横向溢出。没有带日期记录时不画一张全零年度图，仍展示日期待补条目。

### 2.3 图表行为与可访问性

- 柱高代表已知支出原额，与现有月图一致；退款、净支出、售出回收在柱的详情中分别展示，不叠加成一个金额，也不新增图表口径切换。
- 悬浮或聚焦年度柱显示年份、精确支出、退款、净支出、售出回收及未知金额笔数。当前年附“截至今天已记录”；所有年份都不保证记录完整。
- 点击／Enter／Space 进入该年；方向键移动年度焦点，Home／End 到首尾，Escape 关闭浮层。图表提供可读名称与金额，不以颜色作为唯一提示。
- 进入月份后只查看月度金额和全年明细，本次不增加按月筛选明细的第二层导航。月图可聚焦读取金额。
- 从月份返回全部时恢复原年度柱的焦点与图表滚动；页面搜索保留。来源记录已删除则说明并刷新，不打开同名替代。
- 表格及摘要保留精确金额，轴标签可使用元／万元。柱子绘制可转换为图形坐标，聚合与金额比较始终使用整数分。

### 2.4 明细来源拉通

重要支出的房租、订阅付款与虚拟价格也提供来源链接。付款投影携带稳定付款 ID 及所属计划 ID，不能按名称找计划；来源解析复核 ID、归属与资料库 generation 后打开计划只读详情，并单列来源付款的原付款期、实际付款日、实付金额、已记录覆盖期与备注。用户明确点「更正这笔付款」后才打开原付款表单。虚拟价格打开只读服务档案；储值实付打开对应充值记录；物品与独立支出入口沿用已有行为。记录已删或归属改变时提示并刷新，不以同名对象替代。总览、时间轴和搜索的付款来源复用同一入口，返回原页面保留期间、筛选与滚动。

## 3. 年月聚合与缺失值契约

复用现有统一支出来源投影及其去重规则：物品购入、维护、独立支出、已确认周期付款、未关联计划的虚拟价格和储值实付。关联物品的独立支出仅保留来源明细，不再次计入；同一订阅不另生成虚拟支出。

设每个期间的已知支出为 S、退款为 R、售出回收为 A：净支出 N = S − R，允许为负；A 独立展示。退款按退款日期归年归月，不回改原支出年。所有聚合检查整数溢出，不静默截断。

### 3.1 目标读取契约

在现有 `expense_view` 读取模型上扩展，以下是已实现的读取字段及其含义：

| 字段 | 目标含义 |
|---|---|
| `generation`、所选年份、可选年份 | 保留现有资料库校验与期间行为 |
| `annual_totals` | 全部视图的年度桶，升序；单年视图无需重复载入全部年度统计 |
| 年度桶 | 年份、S／R／N／A、参与支出的记录数、其中已知金额数、金额未知数 |
| `months` | 单年固定 12 桶；补足同样的已知／未知信息，全部时为空 |
| 摘要与明细 | 按所选期间读取；日期未知继续单列，不进年月或期间 S／R／N／A |

年份发现、桶聚合、摘要和明细在同一个只读快照中完成；不能分别读取后拼出一页。返回期间必须与请求匹配。前端用请求序号和 generation 丢弃旧期间、旧资料库的迟到响应，错误时显示该次读取失败，不让旧年的数字挂在新年标题下。

### 3.2 显示规则

| 数据状态 | 图表／摘要 |
|---|---|
| 全部金额已知 | 显示精确汇总；明确已付零元仍是已记录事实 |
| 已知与未知混合 | 画已知部分，标“仅已知部分 · N 笔金额待补” |
| 有支出记录但全部金额未知 | 显示“金额待补”，不画成确定零支出；仍能进入该年 |
| 年份只有退款或售出 | 支出标“未记录支出”，退款／回收照实显示；净支出可为负 |
| 月份没有来源记录 | 标“无记录”，零高度表示没有已记录金额，不证明没有实际消费 |
| 日期未知、金额已知 | 单列“日期待补”，不猜今年或今天 |
| 日期与金额都未知 | 保留待补条目，不伪造零或归期 |

未知计数覆盖进入既有支出投影且允许缺金额的来源；不得把不参与金额聚合的关联明细计成未知支出。储值实付未知继续沿用现行档案待补提示，本次不把充值额度或赠送倒推为支出。搜索不改变桶、摘要或待补总量，只改变明细及搜索结果数。

### 3.3 固定金额样例

虚构资料：2024 年旅行支出 1,000 元、订阅实付 120 元；2025 年独立支出 300 元，退回上述旅行款 200 元；2026 年维护费 50 元、另一笔购入金额未知、售出回收 400 元；另有日期未知且金额为 80 元的维护。

| 期间 | 支出已知部分 | 退款 | 净支出已知部分 | 售出回收 |
|---|---:|---:|---:|---:|
| 2024 | 1,120 | 0 | 1,120 | 0 |
| 2025 | 300 | 200 | 100 | 0 |
| 2026 | 50，另 1 笔待补 | 0 | 50，另 1 笔待补 | 400 |
| 全部 | 1,470，另 1 笔待补 | 200 | 1,270，另 1 笔待补 | 400 |

日期待补 80 元单列，不加入以上金额。三个年度桶和各年月份已知部分相加必须与全部摘要一致。

## 4. 关联模型与字段归属

现有 `virtual_assets.plan_id` 继续作为稳定关联依据，不另存一套用于计费的“订阅对象”。有效关系是一项有效虚拟档案对应一项有效计划。停用或最近删除状态也不能靠同名替代 ID。

| 信息 | 唯一事实来源与编辑规则 |
|---|---|
| 服务名称、供应方、标签、网址、档案备注 | 虚拟档案；计划的独立备注保持独立 |
| 计划分类 | 周期计划；旧值保留，新关联不能任意把计划改成另一类 |
| 每期价格、周期、服务日期、付款锚点、试用 | 周期计划及既有生效规则 |
| 暂停、自动续费、最终结束日、后续价格、本期特殊到期 | 周期计划及既有分段／覆盖记录 |
| 实付金额、实付日期、paid／skipped、已付覆盖期 | 既有付款记录；两页复用同一记录 ID |
| 备款提醒 | 既有虚拟档案提醒；周期页可编辑同一设置，不新建第二个提醒源 |
| 累计估算、已记录付款、下一付款候选 | 同一后端推导结果；估算不落为付款事实 |

新建或明确修改共享显示名称时，在同一次保存中更新档案与计划名称。旧名称不同的记录先分别显示“服务名称”和“付款计划名称”；仅打开或修改价格不自动统一名称。提供明确的“统一名称”操作，用户选择采用哪个现有名称或输入新名称。

### 4.1 新建与建立关联

- 虚拟页新建订阅：一次事务创建档案和计划；默认值、试用、付款推导和历史价格规则沿用现行规定，不自动补付款。
- 周期页新建：仍默认独立计划。订阅类计划详情提供“建立关联服务档案”；展示将复用的计划及已有付款，用户填写服务资料后一次保存，仅新增档案，不复制或重新补记付款。
- 建立关联要求计划有效、未被其他有效档案使用；保存时重新核对计划修订与关联占用。历史被删档案引用此计划时，在创建预览说明后续恢复需要核对，不自动恢复旧档案。
- 旧独立虚拟资产没有 plan_id 且保留单次价格时，不提供一键改月费。本次不实现普通解除关联和单次转订阅；需要新建时提示核对旧支出，不能自动删除旧历史。

## 5. 两页界面与编辑行为

### 5.1 列表与详情

两页共用行选择交互：点击行或名称打开只读详情，Enter／Space 同样打开；修改通过详情中的“编辑”。行内“记录付款”独立操作，阻止事件冒泡，不同时打开编辑或切换选择。

| 虚拟页优先展示 | 周期页优先展示 |
|---|---|
| 服务名称、标签／供应方、金额与周期、期限、服务状态、累计费用 | 计划名称、分类／关联服务、金额与周期、下一付款、状态、累计费用 |

现有列可按宽度合并辅助信息，不增加一排重复的金额列。

已关联订阅只有一个详情：周期费用、虚拟资产和重要支出三个入口打开同一个只读弹窗，内容与口径完全一致，不再各列一份。只有一半的对象自然少显示：房租没有服务档案，储值和单次购买没有付款计划，后两者仍用虚拟页右侧栏。

详情按主次分层：

1. **标题区**：名称、状态、每期价格与下次付款；提供方和标签（如有）。
2. **三项主指标**：每期价格（含月均）、已记录付款、当前服务期至。无付款显示“未记录付款”，与明确已付零元区别。
3. **操作**：“记录付款”“结束订阅”突出；“补记历史付款”“整组删除”收在“更多操作”。
4. **详细信息（默认折叠）**：当前服务期、下一付款候选、已付覆盖期、最终结束日、累计估算、分类、试用、开始日期、备款提醒与计划备注；四个日期分开展示，已付覆盖期不冒充整个服务终止日，每个估算邻近注明口径。
5. **来源付款记录**：仅从重要支出进入时置于顶部，并提供“更正这笔付款”。

“关联”只在需要处理时出现：档案停用待核对、档案或计划在最近删除中、服务名称与计划名称不同（提供“统一名称”）。正常状态下详情和列表都不再显示“关联某某”或“查看服务档案／查看付款计划”；虚拟页列表只在付款计划名与服务名称不同时才补一行说明。

### 5.2 编辑、返回与刷新

- 已关联订阅从任一页编辑共享字段，都取得最新双方修订并通过同一领域保存服务提交；已有付款与分段历史不被表单重新生成。
- 普通表单关闭按现行规则丢弃未保存输入，不新增草稿或退出确认。明确保存失败保留输入；提交结果未知冻结重交，保留请求并核对回执。
- 来源跳转携带稳定 ID、generation 和返回上下文；保存或删除后使虚拟、周期、重要支出、总览、时间轴、搜索及提醒相关读取失效。只重读需要的来源，不用重新启动应用才能一致。
- 对应模块关闭时，“查看…”显示不可用原因；当前已开启页面仍能管理其关联计费数据。不能自动开启另一个模块；关闭模块不删除记录，汇总门控沿用现行规则。
- 周期页编辑共享备款提醒也必须沿用虚拟模块的提醒启停门控；虚拟模块关闭时可保留设置，但显示“虚拟资产模块关闭，提醒暂停”，不能经另一页绕过门控安排通知。
- 切换筛选或排序使当前行不可见时关闭该行详情并说明筛选结果；保存成功后按 ID 重读，找不到则关闭详情并刷新。

## 6. 状态与停止续费

有效记录先判断关联是否需核对，再按原日期、排期和服务语义推导，不增加一个可手填的“已结束”布尔字段。

| 操作／状态 | 目标结果 |
|---|---|
| 持续订阅 | 无最终结束日，按原规则安排当前及未来候选 |
| 指定未来结束日 | 使用到该日，两页显示“使用至 YYYY-MM-DD”；允许此前符合规则的付款 |
| 关闭自动续费 | 要求确认最后使用日，优先建议当前服务期末；手填或已保存末日不覆盖 |
| 今天仍等于最后使用日 | 当天仍在服务期；次日才显示已结束 |
| 结束订阅／结束使用与续费 | 明确最后使用日，关闭后续续费，两页一致；保留历史付款和估算依据 |
| 暂停排期 | 不安排未来付款提醒，不改已付覆盖与真实结束日；不自动等同服务终止 |
| 恢复排期 | 沿原生效规则从当前管理，不补造暂停期实付 |
| 再开自动续费 | 已保存的结束日不自动清空；明确选择是否移除期限，历史付款不变 |

新版关联订阅的“停用”入口改为上述明确结束操作，不再只写档案 stopped_on 留计划继续进行。单次与储值的停用语义保持。旧停用档案若计划仍进行，显示关联需核对，不在迁移中自动填结束日。

明确核对旧停用时，展示原 stopped_on 与计划期限：选择“确认已结束”须由用户确认最后使用日，在同一事务设置计划最终结束日、关闭自动续费，并清除该关联档案旧 stopped_on，使以后状态统一从计划推导；原停用日可作建议，不能未经确认写成最终结束日。选择“撤回误记停用”只清除该旧标记，保留原计划期限、暂停与自动续费值，不自动开续费或清期限。其他历史事实不改。新版有效关联档案拒绝单独写入 stopped_on 的旧停用路径，引导上述共同操作。

旧计划缺少可靠服务起点／覆盖锚点时，沿原排期解释；不能从付款日猜服务结束日。结束操作要求明确日期，且不能重写历史已付覆盖。试用内结束保持零估算、不造零元付款；末期仍沿现行整期金额规则，不自动按天退款。

两页的相同状态使用同一推导，界面可分别突出服务与排期，但不能一页写已结束、另一页仍写持续续费。备款提醒只复用已启用设置，付款候选仍取当前及以后未记录期，历史漏记只在补记入口出现。结束、暂停、删除等撤销不再有效的通知；恢复时重新计算，过期提醒不补发。页面操作只维护记录，不声称已经取消平台扣款。

## 7. 整组删除、恢复与永久删除

### 7.1 操作前预览

从档案或计划任一入口发起删除，都读取同一组影响：两者名称、原 ID 与修订、有效 paid／skipped 数、已记录付款金额、将隐藏的范围、关联异常与保护依赖。普通删除只有“取消”和“移入最近删除”，不提供含糊的只删一边选项。

文案示例：“将‘虚构 AI 月订阅’的服务档案与关联付款计划一起移入最近删除。4 笔已记录付款将暂不参与重要支出，可整组恢复。不再使用时可选择结束订阅，以保留历史支出。”

提交必须在事务中重新验证预览涉及的关系、双方修订与影响范围。预览后新增付款、对象改变或依赖改变时要求重新读取影响，不沿用旧确认静默扩大删除范围。

操作影响读取返回可由后端核对的预览标识。标识覆盖 generation、动作、双方／组修订、当前关联成员、受影响付款的 ID／修订／删除状态以及保护依赖；永久清除还覆盖将移除的规则、提醒和组外引用。提交时在写事务中按同一规则重新计算并比较，不信任前端传来的金额或笔数。可采用确定性摘要或已有等价的读取版本保护，具体实现由开发者选择；仅验证两个父对象修订不足以发现新增付款。

### 7.2 软删除与恢复归属

- 删除只将本次有效成员设为最近删除状态，保留关联 ID、价格规则、付款事实和提醒设置。付款继续通过所属计划隐藏，不把所有子付款逐笔改成已删除。
- 记录本次删除的组 ID、成员类型／ID、删除前后修订、哪些成员由本次操作带走，以及明确的恢复成员集合。普通整组删除的恢复集合就是本次带走的两个父对象；历史归组的例外见第 8 节。删除日期不能作为唯一归属依据。
- 最近删除将新整组操作展示为一项“关联订阅”，注明包含 1 个服务档案、1 个计划及隐藏付款数量。筛选档案或计划时可找到同一组，页数与总数按组去重。
- 从任一成员或撤销入口恢复均解析到同一组，一次事务恢复原双方 ID。恢复仅覆盖组中明确登记的恢复成员集合，之前单独删除的付款仍保持删除，组外旧档案不在集合中。
- 关联已被占用、成员被永久删除、删除后修订已变化或保护条件不满足时，整组恢复失败，不先恢复一边。同一已成功恢复请求的回执重放返回原结果；另一个新请求携带已过期组状态时拒绝，不借此改变后来的一次删除。
- 组恢复后，原本有效的付款重新参与汇总一次；重新推导提醒和付款候选，不补造历史付款。提醒调度失败单独报告，不能把已提交恢复说成失败再重做。

每个父对象同时最多属于一个尚待恢复／清除的删除组。组状态区分已删除、已恢复和已永久清除，并有修订约束。恢复后再次删除创建新的组 ID；旧组仅留操作归属记录，不再出现在最近删除列表。旧组的撤销、新恢复请求或迟到响应不能复活新组。父计划仍在最近删除时，子付款的单独恢复继续阻断；对子付款已有删除标记的更正不能绕开父对象保护。

### 7.3 永久删除和清空最近删除

永久删除预览必须覆盖计划下全部付款、规则与提醒，而不只是软删除时有效的付款。检查双方和所有会清除的事实的引用保护；有组外档案引用同一计划时先处理这些旧引用，不静默清空它们的关系。不得删除另一有效档案正在使用的计划。

整组在一个事务中清除，按外键与既有托管文件约束安排顺序；文件清理仅限已确认未被引用的文件。最近删除“清空”同样按组去重处理：不能先清除一个成员，再把另一个成员或同组付款重复清除；被保护的组完整保留，结果列明保留原因。

## 8. 历史关联与升级

“关联需核对”是独立的关系提示，不能用它覆盖真实付款或虚构金额。

| 历史状态 | 读取与允许处理 |
|---|---|
| 双方有效且按 ID 关联 | 直接采用共享编辑及整组生命周期；保持历史名称与金额 |
| 档案已删、计划有效、尚无其他有效档案使用 | 计划提示关联档案在最近删除；可明确恢复档案形成有效组，或删除剩余计划并归成一组 |
| 计划已删、档案有效 | 档案提示付款计划在最近删除；可恢复计划或整组删除 |
| 双方分别历史删除、没有新组归属 | 明确预览后可“恢复关联记录”或登记为一组；升级不自动恢复 |
| 原计划被另一有效档案使用 | 原档案恢复阻断并说明占用；不能恢复后抢占新关系 |
| 档案旧停用，但计划仍进行 | 保留当前事实并提示核对；明确结束日期后协调更新，或撤回误记停用恢复原排期；不自动回填付款 |
| 原计划已被永久清除 | 不造同名计划；保留可读档案信息，提示关联失效，允许明确删除该档案 |
| 没有关联的旧单次投入或独立计划 | 沿用现行规则；同名不代表待修复关系 |

修复关系时只修改用户确认涉及的对象。登记历史删除组应记录哪些成员原本已删、哪些成员本次才删除，并在确认前明确说明“以后整组恢复将恢复这两个父对象”；经这次明确选择，两个父对象进入恢复集合。此前单独删除的付款和组外旧档案不加入集合。没有历史组时，恢复其中一边的用户操作要明确预览另一边的状态，不能继续走旧的单对象恢复留下半组。若用户只要保留当前独立计划，不执行归组或恢复，现状与核对提示保持。

计划已有新的有效关联时，以有效关联作为当前归属，不因它同时被旧墓碑引用而把新服务错误标成异常。旧档案仍保持恢复占用检查；旧档案的单独永久删除不应带走当前有效计划。

若计划没有有效关联，但被多个历史已删档案按 ID 引用，核对界面列出这些候选的名称、ID、删除日期与原关系，由用户明确选择本次要恢复或归组的一个档案。不按名字、删除先后或“最近一条”自动选择；其他候选保留，后续恢复仍受占用检查。当前没有有效归属也不等于所有旧档案都属于本次组。

## 9. 持久化、命令与一致性约束

初始实施基线为 schema 31，订阅分支曾使用 32。合并时主分支已将规划严格载荷兼容提升至 32，因此关联组迁移调整为 schema 33；对两种未发布的旧 32 按规范结构识别并保持资料，旧备份也分别核对。年度统计只增加读取投影，不改应用版本号。

建议新增关联删除组及成员记录，成员类型限定为虚拟档案／周期计划，保存组状态、来源请求 ID、成员删除前后修订及恢复归属。具体物理表名在实现时确定，业务契约以第 7、8 节为准。记录纳入备份 schema 定义、领域验证、摘要和恢复校验；迁移只建立结构，不批量执行删除或修复历史关系。

命令按以下职责组织，名称为建议，未实现：

| 职责 | 要求 |
|---|---|
| 读取关联详情／操作影响 | 一次只读快照返回双方、关系状态、付款摘要与保护原因 |
| 保存关联订阅 | generation、请求 ID、双方稳定 ID、双方 expected_revision；一次事务维护共享字段 |
| 建立关联档案 | 校验计划修订及归属，新增档案并关联已有计划，不新增付款 |
| 删除／恢复／清除关联组 | 操作影响校验、双方修订、组修订／归属、保护依赖与请求回执 |
| 核对旧关联 | 明确动作和成员清单；不依赖名称或删除时间猜对象 |

领域层提供共用服务，UI 不能串联两个普通保存／删除命令模拟事务。原 `recurring_plan_save`、`virtual_save`、`wealth_trash` 和清空入口也须识别关联组：对新关联操作路由到共用服务，或拒绝缺少另一方修订的单对象写入并要求重读，不能只保护新按钮。

已有回执按原指纹先核对重放，不因新关联规则把旧成功请求重新执行；新增请求使用新的命令／指纹版本，避免改变旧请求的序列化含义。同一请求同 payload 返回原结果，不同 payload 拒绝。提交前故障全部回滚；提交后回执丢失通过核对恢复成功结果，不重复保存、删除、付款或恢复。

已关联计费设置更新双方修订，确保另一页的旧表单发生冲突；档案专有资料更正也检查当前关联归属。付款命令仍使用原 plan_id 和付款事实，并拒绝写入已删除计划。所有异步读写遵守 generation；恢复资料库后旧表单、旧预览和旧请求不得写新库。

自动检查执行 `npm run build`、`npm run test:ui`、`npm run check`、`npm test`。前端逻辑测试验证数据与状态规则，Rust 临时 Store 测试验证事务、迁移、回执及恢复；浏览器目视不能代替原生保存与持久化。

原生验收必须用全新隔离身份与虚构资料，覆盖两页编辑、删除恢复、付款、重启与完整备份恢复；提醒实际送达单独核验。不得打开或写入正式库 `local.thingary.main`。自动、浏览器、原生和通知验收分别登记，未验项不得写为全部通过。

界面对照固定使用 1440×940、1024×768、800×700 的内容视口；同组改前／改后使用同一尺寸、风格、浅深色、虚构夹具和所选状态。至少对重要支出、虚拟订阅详情和周期计划详情保留对照。实际原生窗口尺寸另登记，不用浏览器视口截图声称原生窗口缩放已验。
