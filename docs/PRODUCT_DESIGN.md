# 物志 Possio：Local-first Mac 实物资产管理 App 产品设计

版本：v0.4 产品基线 · 更新日期：2026-09-25 · 状态：D01–D13 已确认，A 视觉方向已选；U01 内置素材库待实现，实际工程进度以实施计划为准

本文依据原对话「个人资产管理软件规划」及所附《Local-first Mac 实物资产管理 App 产品设计文档》整理，保留最终收敛到实物资产的方案。早期金融统一方案已被后续范围决策取代。原稿未定的计算与实现细节标为「整理建议」或「待验证」，不视为用户已经确认的开发决策。

竞品依据和平台差异见 [竞品调研](COMPETITOR_RESEARCH.md)，本文是产品需求的唯一完整入口。

持物 iThings 是本产品的首要直接竞品和业务体验参照。当前规划与它在个人物品、心愿、维护、成本和生命周期方面高度重合；Possio 的主要设计方向是围绕 Mac 操作习惯重做这些流程，并聚焦实物。持物的 Mac 兼容入口及待实测边界见竞品调研第 4.1 节，不能把“Mac 可运行”或“本地数据”单独视为独有优势。正式界面设计前，应依据直接比较确认桌面体验的实际价值。

有数同样作为重点直接竞品，优先研究物品展示、成本表达和处置回顾；公开热度证据与待确认能力统一见竞品调研第 4.2 节。竞品研究用于检验现有设计，不自动扩展 P0；日均成本下降不等于物品被充分使用，也不作为鼓励购买的结论。

## 1. 产品定位与用户需求

记录自己买过什么、何时购买、花了多少钱、在哪里买、保修多久、维护过什么、持有多久、最终如何处理，并通过时间轴和统计回顾人与物品的长期关系。

已确认首版交付目标：先做好自己使用的中文 Mac App，稳定后再考虑公开发布；首版不把公开分发、上架和双语作为验收前提。最低系统版本及芯片兼容范围在工程阶段明确。

第一阶段面向自己的实际使用：几十件到数百件重要物品，以电脑、手机、摄影器材、耳机、家电等为主。大额商品购买低频，可能几个月只有几笔；不愿逐笔记生活流水；重视视觉质量、快速录入和多年后的回顾价值。

核心场景是购买时打开、维修时补记、出售时结算、偶尔回顾。金融管理交给独立工具，两套软件之间少量手工录入的成本可接受，无需为统一而引入账户、汇率、交易和快照体系。

产品回答四个问题：

1. **现在拥有什么**：物品、分类、数量及活跃、退役、售出状态。
2. **为重要物品花了多少钱**：当前持有物的购入金额、历史购买总额、期间与分类支出。
3. **持有多久、成本如何**：持有天数、维护投入、售出回收及日均成本。
4. **这些年发生过什么**：心愿、购买、维护、保障、退役和售出的个人时间轴。

日均成本只是成本观察指标，不代表使用频率、满意度或真实市场价值。

## 2. 范围与产品原则

### 2.1 范围

| 当前核心 | 明确排除 | 将来按真实需求评估 |
|---|---|---|
| 实物资产、分类、购买信息、图片 | 股票、基金、债券、金融账户、金融净资产 | 虚拟资产、软件授权、订阅 |
| 生命周期、保修、维护、出售 | 日常收入支出、餐饮流水、信用卡账单、复式记账 | OCR、条码、设备型号识别 |
| 心愿转资产、时间轴、统计 | 银行/微信/支付宝同步、在线估值依赖 | 可选同步、二手估值、自然语言查询 |
| 本地存储、导出、备份恢复 | 云账户、多用户协作、部署 Web Server、Docker | Windows 等其他平台 |

房租和订阅虽然在早期讨论出现过，也不属于当前实物 MVP。AppleCare 等与物品直接相关的延保可作为 Warranty 记录，不由此扩展成订阅系统。

### 2.2 原则

- **Local-first**：核心能力离线可用，无需注册；数据保存在本机 SQLite 和文件系统。
- **无需常驻**：双击应用即可使用；完整退出后不留下项目自建服务或守护进程。关闭窗口与退出应用的行为应明确。
- **Desktop-first**：侧栏、表格、详情面板、键盘操作，充分利用 Mac 屏幕；不直接放大手机界面。
- **低录入成本**：新增资产一屏完成基本信息，更多字段渐进展开。
- **数据可带走**：可读导出与完整备份分别服务分析和恢复，附件也必须纳入恢复。
- **完成度优先**：先做好资产详情、快速新增、时间轴、统计和备份。

视觉方向参考原讨论中的 Wealthfolio、Linear、Raycast、Arc 和 Apple 应用：安静、清晰、信息密度适中。它们是体验参考，不构成功能或代码复用承诺。

## 3. 信息架构与桌面交互

```text
Overview 总览
Assets 资产
  All / Active / Retired / Sold
Wishlist 心愿
Timeline 时间轴
Insights 统计
Settings 设置
```

采用左侧导航 + 主内容区；列表单击可打开右侧详情面板，双击进入完整详情。返回后保留筛选、排序和滚动位置。浅色、深色、跟随系统属于基础体验。

### 3.1 Overview

顶部显示当前持有物购入金额、当前持有数量、平均持有时间、进行中心愿数；活跃数量单独标明。避免将 `Active` 数量误标为全部持有数量。

中部展示累计购入金额趋势、按购入金额的分类分布；分类图建议圆环配列表。趋势描述的是历史购入累计金额，不是市场估值曲线。底部展示最近 5–8 个事件，点击进入关联物品或心愿。

### 3.2 Assets

- Grid 用于看图片和回顾；卡片展示封面、名称、品牌、购买金额、状态、持有时长。
- List 用于比较与检索；列包括名称、分类、购入日期、购入金额、状态、持有时长，可按列排序。
- 支持按生命周期、分类、保障状态筛选，按名称等搜索；标签筛选随 P1 标签功能提供。
- 第一屏新增字段：名称必填，分类、价格、购买日期、封面可填。更多详情折叠展示品牌、型号、渠道、序列号、保修、备注。
- 未知购买价格或日期允许留空，界面明确显示未知，不自动写成零或今天。

详情页包括封面与名称、品牌分类、编辑与生命周期操作、购买资料、持有与成本、保障、维护、附件及单件时间轴。重要信息应在同一详情中看全，不为每条资料增加跳转。

### 3.3 搜索与快捷键

基础搜索覆盖资产名称、品牌、型号、分类、备注和序列号；P1 全局搜索加入心愿、标签与操作命令。

| 快捷键 | 意图 |
|---|---|
| ⌘N | 新增资产 |
| ⌘F | 当前页面搜索 |
| ⌘, | 设置 |
| ⌘E | 编辑选中资产 |
| ⌘K（P1） | 全局搜索与命令面板 |

命令面板可提供新增资产/心愿、记录维护、标记售出、打开设置、导出备份。以上为交互设计，需在实现时处理焦点和系统快捷键冲突。

### 3.4 基础体验

空列表应直接引导新增，筛选无结果可一键清除；表单错误就地提示并保留输入；保存失败不能显示成功或丢失输入。可访问名称、键盘焦点、文字对比和图片占位作为基础质量要求，不依赖新增功能扩张。

## 4. 资产与生命周期

### 4.1 资产资料

| 分组 | 字段与要求 |
|---|---|
| 识别 | 名称、品牌、型号、单一分类、封面；序列号可选 |
| 购买 | 实付购入价、币种、购入日期、购买渠道 |
| 扩展购买信息 | 订单号、发票号、卖家、购买链接、原价与折扣；不是 P0 必填 |
| 生命周期 | 当前状态、退役日期、售出日期与售价 |
| 其他 | 多标签（P1）、备注、创建/修改时间 |

已确认首版一条资产表示一件可独立维护、退役或售出的物品，不做数量库存或组合拆分。两台同型号设备分别记录；成套且整体处置的物品可作为一件。

不要同时以 `purchase_price` 和 `actual_price` 存储两份含义相同的实付价格。原价与折扣为扩展资料，统计以实付价为准。

### 4.2 状态独立于保障

| 状态 | 含义 | 是否仍持有 |
|---|---|---|
| Active 活跃 | 仍在主要使用 | 是 |
| Retired 退役 | 不再主要使用，但仍拥有 | 是 |
| Sold 售出 | 已完成出售 | 否 |

P0 支持 Active → Retired、Active → Sold、Retired → Sold。流程保留 Retired → Active 重新启用并记录事件；状态动作按时间顺序，冲突由用户更正源记录，不自动重写历史。Returned / Lost / Gifted 属于后续扩展，不能简单套用售出语义。

保修独立显示，资产可同时为 Active + Covered。退役不是删除，售出不是删除；二者都保留历史购买与维护信息。

### 4.3 售出

标记售出时输入日期和实际售价，平台、买家及备注为选填。保存时更新资产、记录售出事件、刷新当前持有统计和净成本，整体成功或整体失败。销售日期不能早于购入日期；待售物品不能提前按已售处理。

出售数据录错时应通过更正业务记录同步修正时间轴和统计，不能靠另加一条无关联事件修补。已确认允许撤销误记售出，恢复到该次售出前的 Active 或 Retired 状态；清除当前有效售出结算，并同步统计与时间轴。真实售出后又购回则另建资产，原资产保留真实处置历史；退货作为后续状态扩展，不纳入 P0。

## 5. Warranty 与 Maintenance

### 5.1 Warranty

一件资产可有厂家保修、延保、AppleCare、商店保修或其他保障。记录类型、提供方、起止日期和备注，可关联附件。

保障状态自动计算：未记录保障、保障中、即将到期、已到期。已确认截止日当天仍有效、30 天内到期提示「即将到期」；未来才生效或缺失日期应单独说明，不能误算成当前已覆盖。多份保障分别展示，摘要以当前有效保障判断。

P1 评估在到期前 30/7/1 天提醒。设计意图是由系统调度本地通知，不要求应用常驻；所选桌面技术栈能否在退出后可靠投递、如何更新/取消计划、权限拒绝后的降级均待真实打包验证。P0 在应用内展示保障状态即可。

### 5.2 Maintenance

记录日期、类型、标题、描述、金额、币种、服务商和附件。已确认维护日期可未知，已知费用仍计入总成本，但不伪造期间归属；售出后可补录持有期间的历史维护。类型包括维修、保养、清洁、部件更换、升级、其他。例如相机清洁 ¥300，既应出现在维护列表，也应出现在时间轴中。

同一笔成本只记录一次：升级如果作为维护类型保存，生命周期成本不能再加一次 `upgrade_cost`。金额未知应与零费用区分。P0 支持维护新增、编辑、软删除、从统一最近删除恢复及对应统计更新；保障误删同样可恢复。P1 补充 PDF 等附件。

## 6. 成本与统计口径

本节统一各页面的术语。人民币范围、持有成本、自然日边界和缺失值等核心规则已经用户确认，决策记录见第 15.2 节。

### 6.1 指标定义

| 指标 | 范围 / 计算 |
|---|---|
| 当前持有数量 | 未删除的 Active + Retired |
| 活跃数量 | 未删除的 Active |
| 当前持有物购入金额 | 当前持有物的已知实付购入价合计 |
| 历史购入金额 | 所有未删除资产的已知购入价，包括已售出与退役 |
| 期间购入金额 | 购买日期位于期间内的购入价合计 |
| 累计购入趋势 | 按购买日期累计，出售不回减；不是当前持有价值 |
| 总投入 | 购入价 + 已记录维护费用（含升级） |
| 净生命周期成本 | 总投入 − 实际售出回收金额 |
| 日均持有成本 | 总投入 ÷ 持有天数 |
| 售出后净日均成本 | 净生命周期成本 ÷ 截至售出日的持有天数 |
| 售出保值率（P1） | 售价 ÷ 购入价；购入价为零或未知时不计算 |

「资产价值」默认指历史购入金额，不是二手估值或金融净资产。时间轴金额是展示信息，不与业务表重复累加。

### 6.2 日期与退役

已确认采用自然日口径：

```text
截止日 = 已售出 ? 售出日期 : 今天
持有天数 = max(1, 截止日与购买日期的自然日差 + 1)
```

购买当天按 1 天，避免除零；未来购买进入心愿，历史资产不能使用未来购入日期。售出后天数固定。Retired 仍持有，因此「日均持有成本」继续摊薄；若以后增加「活跃使用成本」，需记录活跃区间，不能把两者混称为使用成本。

购买日期未知时不展示持有天数或日均成本；购买金额未知时成本标为不完整，汇总同时展示未计入数量。不得以零代替缺失数据，让不完整统计看起来完整。

### 6.3 金额与币种

用户已确认：P0 只使用人民币（CNY），资产、维护、售价及心愿预计价格均使用人民币，首版不提供币种切换、汇率输入或自动换汇。currency 字段可为未来迁移保留，但其存在不意味着界面已支持多币种；多币种功能以后另行设计。

金额使用最小货币单位整数或精确定点方案；展示时再舍入。购入、维护、售价通常非负，零购入价可用于赠品。售出所得大于总投入时可出现负净成本，应如实显示并说明，不强行截断为零。

例：购入 ¥16,999，维护 ¥300，售价 ¥5,000，持有 1,000 天，总投入 ¥17,299，净成本 ¥12,299，毛日均 ¥17.30，净日均 ¥12.30。

## 7. Wishlist：购买前的生命周期

字段包括名称、分类、预计价格、币种、优先级、加入时间、目标日期、链接、封面、备注、状态。状态为 Ongoing / Achieved / Abandoned。

页面支持进行中、已实现、已放弃筛选，Grid/List 切换，按最近加入、优先级、价格、目标日期排序；自定义排序放在 P1。预计总额仅统计进行中且价格已知的心愿，不计入购入资产金额。

「标记已购入」流程：

1. 从心愿打开确认表单，填写实际购入日期、价格、渠道，可补保修。
2. 创建 Asset，将 Wishlist 更新为 Achieved，并设置 `converted_asset_id` 与实现时间。
3. 写入关联的心愿实现、购买事件，保留原来的加入时间、预计价格和备注。
4. 保存成功进入资产详情；重复点击不能生成重复资产。

上述数据库写入在同一事务内完成。原图和附件的复用/复制采用可恢复的文件操作流程。资产详情可以追溯原心愿，心愿保留历史，不因转换而消失。

## 8. Timeline：个人物品档案

按实际事件日期从新到旧排列，分年/月，支持全部、购买、维护、退役/售出、心愿等筛选，点击进入关联实体。

| 事件 | 来源 |
|---|---|
| 资产建档、购买、退役、重新启用、售出 | 资产业务操作 |
| 维修、清洁、保养、升级 | Maintenance |
| 添加保障、保障到期 | Warranty |
| 加入心愿、实现心愿、放弃心愿 | Wishlist |
| 搬到办公室、更换键盘等个人备注 | 手工事件（可作为后续增强） |

建档时间与真实购买时间分开；补录旧物时不能把今天当作购买日期。详情里的单件时间轴和全局时间轴使用同一来源。

系统事件关联源业务记录，修改购买日期、维修金额或出售记录时保持一致。手工事件可独立编辑；系统事件的业务金额从来源更正，不允许产生第二套事实。心愿实现与购买属于同一次转化，可组合展示，不能统计成两次购买。

保障到期无需后台写任务：可查询时派生，或应用启动时幂等补齐；实现时二选一。延保日期更正后旧到期信息应更新，重复启动不得制造重复事件。

## 9. Insights

| 模块 | 展示内容 | 范围 |
|---|---|---|
| 状态总览 | Active / Retired / Sold 数量 | P0 |
| 分类分布 | 分开呈现数量占比与购入金额占比 | P0 |
| 购买趋势 | 周/月/季/年与全部范围；按购买日期聚合 | P0 先月/季/年/全部，周视图后续 |
| 持有周期 | 小于 6 个月、6–12 个月、1–2 年、2–3 年、3 年以上；平均、中位数、最长 | P0 |
| 日均成本排行 | 可按成本排序，显示持有天数、适用口径与缺失数据 | P0 |
| 售出分析 | 购入价、售价、持有时长、净成本、保值率 | P1 |

统计默认应显示对象范围和期间。当前持有与历史全部不混合，当前毛日均与已售出净日均分开展示。不把各物品日均成本的简单平均称为「每件平均消费」；若增加组合日均指标，需另定义公式。

## 10. 分类、标签、渠道与图片附件

分类为单选，可新增、改名、排序和选择图标；删除被引用分类应先迁移物品或改为未分类。默认分类可包含电脑、手机、平板、摄影、音频、家电、家具、穿戴、游戏、车辆、户外、收藏及其他。

标签为多选，P1 实现，用于工作、旅行、品牌等交叉标记，不替代分类。购买渠道独立管理，预置 Apple Store、京东、淘宝、Amazon、线下、二手、其他并允许自定义；按渠道分析不进入 P0。

新增资产默认从内置素材库选取封面与图片，首批复用八种 Demo 原创插图（D13）；可不选图直接建档。自有图片导入保留为次要入口，已有照片及附件不受影响。

图片目标为一张封面 + 多个附件，格式包括 JPG、PNG、HEIC、WebP；PDF 附件为 P1。HEIC 等解码、预览与导出的兼容性需验证，不因写入设计就视为已支持。

附件存独立文件，SQLite 保存相对路径、类型、哈希等元数据，不把全部图片塞入 BLOB。应复制到应用托管目录，用户移动原文件后仍能查看。缩略图可放缓存，备份必须覆盖原始托管文件。每个附件关联资产、维护、保障或心愿，封面通过明确引用确定。

## 11. 逻辑数据模型

下表是产品级模型，不是已定稿 SQL migration。以 UUID 等稳定 ID 建立关联；日期表示业务自然日，审计时间表示时间戳。

| 实体 | 核心字段 |
|---|---|
| Asset | id, name, brand, model, serial_number, category_id, purchase_date, purchase_price, currency, purchase_channel_id, status, retired_at, sold_at, sale_price, sale_platform, buyer, cover_attachment_id, notes, created_at, updated_at, deleted_at |
| Category | id, name, icon, sort_order |
| PurchaseChannel | id, name, sort_order |
| Warranty | id, asset_id, type, provider, start_date, end_date, notes, created_at, updated_at |
| Maintenance | id, asset_id, type, date, title, description, cost, currency, provider, created_at, updated_at |
| Wishlist | id, name, category_id, expected_price, currency, priority, target_date, url, cover_attachment_id, notes, status, created_at, achieved_at, abandoned_at, converted_asset_id, updated_at, deleted_at |
| AssetEvent | id, entity_type, entity_id, event_type, event_date, title, description, amount, currency, source_type, source_id, metadata_json, created_at, updated_at |
| Attachment | id, entity_type, entity_id, type, filename, relative_path, mime_type, size_bytes, sha256, created_at |
| Tag / AssetTag（P1） | id, name；asset_id, tag_id 联合唯一 |

关系：Asset 属于一个 Category 和可选 PurchaseChannel，有多条 Warranty、Maintenance、Attachment、AssetEvent；Wishlist 最多转换为一个 Asset。

约束与一致性要求：

- 打开 SQLite 外键约束；重要写操作使用事务；评估 WAL 与备份方案。
- 多态 `entity_type/entity_id` 不能靠一个普通外键同时指向多张表，需由应用校验及删除流程保证，或在工程设计时改为明确关联表。
- 系统事件以源记录标识保证幂等；事件金额不作为第二个账本。
- Wishlist 转换应有唯一约束或幂等键，防止重复资产。
- 文件写入不能假装被 SQLite 事务自动回滚：使用临时文件、提交后移动和失败清理，并避免删除共享附件。
- 迁移前备份，记录 schema 版本，升级失败不能留下半迁移状态。数据库版本、应用版本、备份格式版本分开管理。

## 12. 本地存储、迁移与恢复

```text
~/Library/Application Support/<实际应用标识>/
  app.db
  attachments/
    <entity-id>/...
  backups/
  cache/
```

具体应用标识和沙盒路径在打包时确定，不在业务代码硬编码用户名。

### 12.1 导出与导入

- **CSV 导出（P0）**：默认导出全部未删除资产，包含已售出；可读资产表用于迁移和分析，不声称覆盖全部关联信息。
- **JSON 结构化导出（P1）**：包含稳定 ID、关联、schema 版本和附件清单；文件本体与导出关系需说明。
- **CSV 导入（P1）**：名称、分类、品牌、型号、日期、价格、币种、渠道、状态、备注；映射后预览，报告有效/无效行和原因，确认后提交。
- 导入必须定义重复记录策略与失败回滚；不得悄悄覆盖现有资产。未知分类/渠道的创建由预览明确告知。

### 12.2 完整备份（P0）

```text
Possio-backup-<date>.zip
  manifest.json
  database.sqlite
  attachments/
```

清单包括备份格式版本、应用/schema 版本、创建时间和校验信息。备份应获得一致的数据库快照并覆盖附件，不能在 WAL 存在时简单复制一个可能不完整的主库文件。

恢复先检查版本、完整性、路径和关联，再写入临时目录；保留当前数据的恢复前备份，全部通过后切换。失败不得破坏原数据。P0 以完整替换恢复为目标，合并恢复不默认纳入。

P1 可在启动时检查距离上次成功备份是否超过 7 天，并按可配置保留策略备份；应用退出时备份仅作为补充，不能作为唯一可靠路径。自动备份无需常驻服务。备份和附件也属于用户私密资料；加密备份属于后续评估项。

### 12.3 删除与恢复

已确认：P0 使用软删除，统一“最近删除”管理资产、维护、保障三类记录，支持按类型筛选及恢复；删除期间排除相关常规统计，首版不自动永久清空。P1 再完善批量清理、保留策略和永久清除确认。恢复资产恢复其原本有效的关联档案，不自动恢复此前独立删除的维护/保障；父资产已删除时，恢复子记录先引导恢复父资产。删除操作不得破坏共享附件。删除不等于售出或退役。

## 13. 技术方向与边界

原讨论推荐 Tauri 2 + React + TypeScript + Rust + SQLite，作为后续工程设计起点；UI 候选为 Tailwind CSS、Radix/shadcn，图表在 ECharts 与 Recharts 中择一。本文不锁定依赖版本或给出未经验证的 API 用法。

```text
React UI
   │ Tauri Command / IPC
   ▼
Rust Application / Service
   ├─ Repository → SQLite
   └─ Storage → Local File System
```

React 不直接写 SQLite。Rust 应用层统一做输入校验、生命周期动作、成本计算和事务边界；前端管理交互状态和展示。核心计算可独立验证，不能由每个页面复制一套公式。

发布形态目标为内嵌前端资源的桌面 App，不运行额外 Express/HTTP API 服务。开发用前端服务器不等于发布时必须启动服务器，验收以打包应用为准。选用 Tauri 本身也不会自动保证启动速度、包体或零残留进程，必须实测。

原稿建议目录按功能组织前端，后端分 commands、services、repositories、models、migrations、storage。此处仅保留组织原则，不在文档整理阶段创建空代码目录或确定完整工程结构。

## 14. 交付阶段

### P0：可长期自用的闭环

- Assets：新增/编辑/搜索/分类/渠道/封面/购买信息，Grid/List 和详情。
- 生命周期：Active、Retired、Sold；准确的持有范围与售出结算。
- Warranty：起止日期与自动保障状态；Maintenance：维护记录与成本。
- Wishlist：新建、放弃、实现并转换资产，保留关联历史。
- Timeline：购买、维护、保障、退役、售出、心愿事件，避免重复。
- Overview / Insights：数量、购入金额、分类、购买趋势、持有周期、日均成本。
- System：离线 SQLite、托管图片、完整备份恢复、CSV 导出、深浅主题。
- 删除安全：资产、维护、保障统一最近删除、软删除与恢复，首版不自动永久清空。

P0 按完整用户流程分批实现：先完成资产录入、持久化、详情、更正与基本恢复，再补充维护、心愿和统计。首个可用开发切片不代表完整 P0 交付。

### P1：完善迁移与桌面效率

CSV 导入、JSON 导出、PDF 附件、保障提醒、自定义标签与排序、命令面板、完善回收站、自动备份、售出保值率、高级统计、自定义总览。原稿的「自定义状态」保留为待设计项，必须先定义每种状态是否仍持有、是否停止计时，不能直接开放任意字符串。

### P2：真实使用后评估

可选 iCloud/文件同步、虚拟资产和订阅、OCR、条码、设备识别、二手价格估值、AI 搜索或自然语言查询。同步不能简化成把正在写入的数据库直接丢进同步盘，需独立解决一致性和冲突。

AI 不属于首版。积累数据后，再评估诸如「过去三年电子产品花了多少钱」的查询是否真能改善体验。

## 15. 验收与待冻结决策

### 15.1 关键验收场景

1. 离线打开打包应用，新增资产，退出后重新打开仍存在；无项目自建后台服务残留。
2. 同一资产可同时显示 Active 和 Covered；退役后仍计入持有，售出后不计入。
3. 购买当天不除零，缺失价格/日期明确提示，售出后持有天数不继续增长。
4. 心愿转资产只生成一件，日期、实付价、历史与关联一致；任一步失败不产生半完成状态。
5. 编辑维护费用或售出日期后，详情、总览、统计和时间轴同步；升级成本不重复计入。
6. 删除后可恢复；退役与出售保持完整历史。分类调整不造成悬空资产。
7. 把完整备份恢复到全新数据目录，资产、心愿、维护、保障、时间轴及图片均可用；损坏备份不覆盖原数据。
8. 列表、详情、空状态、深浅主题和主要键盘路径可实际使用，无需读工程说明才能操作。

优先验证计算边界、事务失败与备份恢复；文档齐全或结构检查通过不能替代产品验收。

| 日期未知 | 购入 ¥1,000，日期留空 | 购入金额可计入；持有天数、日均和按购入日期的趋势不计算，并说明原因 |
| 撤销售出 | 撤销从 Retired 状态发生的误记售出 | 回到 Retired、仍持有；清除当前有效售出字段并修正事件与统计 |
| 删除与恢复 | 删除含维护、保障、图片的资产后恢复 | 删除期不入常规统计；恢复同一资产及关联档案，不新增重复记录 |

其他不可忽略的验收例包括重复点击心愿转换、未知维护金额、重叠保修、保存失败、附件缺失、损坏备份恢复。具体输入输出在 Spec 阶段补全，不能只覆盖正常页面。

个人软件的成功标准是能长期记录、不丢数据、快速录入、回顾有价值，并且停止维护后仍能导出。工程任务拆分及 Codex/Hermes 模型分工不属于本产品文档。

## 16. 核心用户流程（交互草案）

状态：2026-09-24 已依据 D01–D12 细化；输入和失败结果见功能规格，像素与实际交互验收仍待实现后验证。此处规定用户路径及页面状态，不等于已经做出 UI，也不锁定组件、像素或工程实现。业务语义沿用前文，具体字段不在这里另建一份清单。

### 16.1 所有流程共用的交互规则

- 用户操作在成功保存前不改变已保存档案或汇总。保存中防止重复提交；失败保留输入并提供重试。
- 输入合法性在对应字段附近说明，不用笼统的“操作失败”代替可修正原因；金额统一显示人民币。
- 有未保存改动时，关闭表单可选择继续编辑或放弃；没有改动则直接关闭。取消不产生业务事件。
- 错误同时区分用户可修正的问题和存储失败，不向普通界面暴露 SQL、IPC 或文件系统堆栈。
- 完成操作后保持对象可见，并更新相关统计；从列表打开的详情应尽量保留筛选与滚动上下文。
- 失效、被删除、未找到和加载失败不是同一种空状态，分别提供恢复、返回或重试入口。

### F01：第一次使用与新增资产

**用户目标：** 快速记录一件重要物品，即使尚不清楚全部购买资料。

入口：首次打开总览的“添加第一件资产”、Assets 的“新增资产”、⌘N。

1. 初次进入无需登录，也不强制完成分类设置或观看引导。总览空状态解释用途，并提供新增入口。
2. 打开统一新增表单。名称必填；分类、购买金额、日期和图片按需填写，品牌、渠道、序列号等在“更多资料”展开。
3. 未知金额或日期保留为空；日期输入可提供“今天”快捷选择，但不能默认把未知旧物记为今天。已有分类可选择，暂不分类也可保存。
4. 默认从素材库选择示意图并预览，也可通过次要入口导入自有图片；无法读取或格式不支持时说明原因，允许移除图片继续保存。用户选择保留的图片必须成功保存，不能静默丢弃。
5. 保存成功后进入该资产详情，状态为 Active；出现建档信息，只有已知购买日期才显示对应购买事件。

**成功检查：** 新记录只产生一次；图片托管后原文件被移动仍可读取；回到列表能找到它。重新打开应用后记录仍存在。

**取消/失败：** 取消不留下半条资产；名称为空不能提交；日期在未来提示使用心愿；存储失败保留表单和已选图片供重试。

### F02：查找、查看与更正资产

**用户目标：** 找到物品，核对资料并修正补录信息。

入口：Assets 列表/网格、总览最近事件、Timeline 关联对象。

1. 通过名称或基础资料搜索，并可按分类、生命周期或保障状态筛选。
2. 列表选择资产打开详情面板；进入完整详情可查看成本、保障、维护和时间轴。详情中的“编辑”或 ⌘E 进入更正表单。
3. 补填未知日期/价格，或修正名称、渠道等资料；保存后原记录更新，不新增另一件资产。
4. 涉及购买日期和费用的更正同步成本与有效事件。归档状态操作通过明确动作入口完成，不能在普通字段编辑里无提示变成另一种状态。

**成功检查：** 列表、详情和统计使用一致的资料；更正购买日期不会把建档时间改成旧日期。返回列表保留筛选，若更正后不再匹配筛选则说明原因。

**取消/失败：** 输入未保存时原资料保持不变；无搜索结果提供清除筛选；误删对象从链接进入时提供“前往最近删除”，而不是显示数据库错误。

### F03：记录维护与保障

**用户目标：** 在同一物品档案中补记维修投入和保障资料。

入口：资产详情中的“记录维护”“添加保障”；两类记录使用独立表单和成本语义。

1. 维护表单填写发生日期、类型、标题、费用和服务商等；费用可为零或未知。升级是一种维护，不能在另一处再累计同一笔费用。
2. 保存后维护列表和时间轴显示同一次业务记录；成本立即依据完整性和金额更新。维护费用未知时说明成本不完整。
3. 保障表单填写类型、提供方与日期，可连续添加多份。保存后详情分别展示，并更新有效保障摘要；保障变化不改变 Active/Retired/Sold。
4. 从记录菜单更正或删除误记维护/保障，相关有效事件和统计同步变化；删除前说明影响。

**成功检查：** ¥200 的维护只增加 ¥200 总投入；多份保障不会变成多个生命周期状态；保障过期不会把资产自动退役。

**取消/失败：** 日期矛盾就地提示；保存失败不出现虚假的新记录。P0 不以通知权限、PDF 上传或常驻服务作为前提。

### F04：心愿新建、放弃与转资产

**用户目标：** 保留购买前的想法，买到后自然接入资产档案。

入口：Wishlist 的“新增心愿”；已存在的 Ongoing 心愿详情中的“已购入”。

1. 新建心愿时填名称，其余预计价格、分类、优先级、目标日期和链接按需补充。保存后进入进行中列表。
2. 不再考虑的心愿可“放弃”，保留记录并进入已放弃筛选，不生成资产或消费。
3. 选择“已购入”后打开资产确认表单，沿用名称、分类和图片，填写实际价格/日期等。预计价格仅作参考，不能静默当成实际价格。
4. 确认后一次完成资产创建、心愿实现和关联事件，跳转新资产详情，提供返回原心愿的入口。
5. 已实现心愿显示关联资产，不再提供第二次转换按钮；关联资产被软删除时引导恢复，不能默认再次转换。

**成功检查：** 心愿原始预计价和加入日期保留；实际购买金额只计一次；资产能回溯到原心愿。

**取消/失败：** 取消确认表单时心愿保持进行中；任一步保存失败不得留下半转换；连续点击只创建一件资产。

### F05：退役与重新启用

**用户目标：** 记录暂时不再使用，仍保留拥有关系。

入口：Active 资产的“标记退役”；Retired 资产的“重新启用”。

1. 选择退役日期，可补备注，界面说明“仍计入持有，日均持有成本继续计算”。
2. 保存后状态为 Retired，活跃数量减少，持有数量不变；时间轴增加退役事件。
3. 重新使用时选择“重新启用”，填写日期，状态回到 Active，并新增对应事件；不清掉之前的退役历史。

**成功检查：** 重新启用不会重置购买日期、持有天数或维护成本。Sold 不能直接点“重新启用”，必须区分误记售出和真实购回。

**取消/失败：** 取消或失败保留原状态；日期不能早于购买或前一有效生命周期动作（资料已知时）。补录复杂倒序历史的处理留到 Spec 明确，不自动改写后续历史。

### F06：售出、修改与撤销误记

**用户目标：** 保存真实处置结果，同时允许更正录入错误。

入口：Active/Retired 资产详情的“标记售出”；Sold 详情中的“修改售出记录”“撤销误记售出”。

1. 填写售出日期与实际售价，平台、买家和备注选填；展示已知总投入与结算预览。出售金额是必填的实际数字，可为零但不能以空值冒充零。
2. 确认后资产进入 Sold，退出当前持有统计；持有天数固定到售出日，展示净生命周期成本及净日均持有成本。
3. 仅金额或日期写错时修改原售出记录，保持同一出售事实；保存后更正有效时间轴和结算。
4. 整次出售误记时选择撤销，预览将恢复的状态。确认后回到该次售出前的状态，撤掉当前有效结算和有效售出事件，保留必要更正记录供内部追溯。
5. 实际卖出后又买回时，从“新增资产”记录新购入；原 Sold 档案继续保留，不复用撤销入口改写真实历史。

**成功检查：** 从 Retired 售出再撤销应回到 Retired；撤销后天数重新计算到今天；出售收入不直接写入任何金融账户。

**取消/失败：** 日期不合法时阻止提交；取消不改变状态；结算资料不完整时明确标注，不展示虚假的精确净成本。

### F07：统一最近删除与恢复

**用户目标：** 去除误录资料，同时可以找回误删档案。

入口：资产详情及维护/保障记录的“删除”；Settings 中的“最近删除”。

1. 删除确认说明资产将移入最近删除，关联记录一起隐藏且退出常规统计；这不代表退役或出售。
2. 删除资产成功回到原列表；删除单条维护/保障后留在所属资产详情。两者都提供前往最近删除的入口。常规搜索与 Timeline 不继续展示已删除资产的有效业务记录。
3. 最近删除统一列出资产、维护、保障，可按类型筛选；显示名称、类型、所属物品、适用的原状态和删除时间，可选择恢复；首版不自动永久清空。
4. 恢复时保留原 ID、原生命周期和资料，恢复此前有效的关联档案；独立删除的维护/保障仍保持删除。子记录的父资产若已删除，先引导恢复父资产；心愿转换关系继续指向同一资产。

**成功检查：** 恢复一件 Sold 资产后仍为 Sold，不重新算入当前持有；恢复不重复创建时间轴事件、维护或图片。共享文件与其他资产不受影响。

**取消/失败：** 删除取消不改变资料；恢复失败保留最近删除项和已有文件，展示重试。仅关闭通知式提示不等于永久失去恢复机会。

### F08：导出备份、CSV 与恢复

**用户目标：** 带走数据，并能在需要时完整恢复。

入口：Settings 的“数据与备份”，明确分开“完整备份”“CSV 导出”“从备份恢复”。

1. 完整备份选择目标文件位置，说明包含资产、关联记录和托管图片；生成并验证完成后才提示成功与保存位置。
2. CSV 导出明确仅为可读资产表，不包含完整附件和全部关联历史，不用它替代备份。
3. 恢复时先选择备份并检查格式、版本和完整性；展示备份时间、记录概况及“替换当前资料”的影响。
4. 用户确认后先保护当前数据，再恢复；成功后重新加载总览和列表，并报告结果。
5. 完整备份应保留软删除记录及其附件，保证恢复后“最近删除”仍可用。缓存可重建，不属于用户档案。

**成功检查：** 在全新数据目录恢复后，关联资料与图片可读，金额/状态一致；恢复不会把已售出或已删除资产变成活跃。

**取消/失败：** 取消选文件不产生任务；恢复前校验失败不动现有数据；恢复中失败保留可用的原数据与备份；不能只因为 ZIP 文件存在就提示完整成功。

### 16.2 页面与关键状态覆盖

| 页面 | 必须在原型中考虑的状态 |
|---|---|
| 总览 | 第一次使用、已有资产、部分价格/日期未知、近期无事件 |
| 资产列表/网格 | 正常、无资产、筛选无结果、选中详情、对象因更正不再匹配筛选 |
| 新增/编辑 | 最小字段、更多资料、零元、未知、日期非法、图片失败、保存中、保存失败、放弃改动 |
| 详情 | Active/Retired/Sold；保障独立；无图；成本不完整；有/无维护；关联心愿 |
| 心愿 | 进行中、已实现、已放弃、转换中/失败、关联资产被删除 |
| 时间轴 | 有事件、无事件、筛选无结果、更正后只显示有效业务事实 |
| 设置与数据 | 最近删除空/非空、恢复失败、备份成功/失败、损坏或不兼容备份 |

已完成上述代表性页面原型，用户选择 A「静序」作为视觉基线，详见 [UI 设计](UI_DESIGN.md)。现将这些流程细化为 [功能规格](FUNCTIONAL_SPEC.md) 中的验收定义；其余 P0 页面继续沿用 A 扩展。全部样例保持虚构，不依赖真实个人资料或外部账号。
