持物 iThings 是本产品的首要直接竞品和业务体验参照。当前规划与它在个人物品、心愿、维护、成本和生命周期方面高度重合；Possio 的主要设计方向是围绕 Mac 操作习惯重做这些流程，并聚焦实物。持物的 Mac 兼容入口及待实测边界见竞品调研第 4.1 节，不能把“Mac 可运行”或“本地数据”单独视为独有优势。正式界面设计前，应依据直接比较确认桌面体验的实际价值。

有数同样作为重点直接竞品，优先研究物品展示、成本表达和处置回顾；公开热度证据与待确认能力统一见竞品调研第 4.2 节。竞品研究用于检验现有设计，不自动扩展 P0；日均成本下降不等于物品被充分使用，也不作为鼓励购买的结论。

## 1. 产品定位与用户需求

记录自己买过什么、何时购买、花了多少钱、在哪里买、保修多久、维护过什么、持有多久、最终如何处理，并通过时间轴和统计回顾人与物品的长期关系。

已确认首版交付目标：先做好自己使用的中文 Mac App，稳定后再考虑公开发布；首版不把公开分发、上架和双语作为验收前提。最低系统版本及芯片兼容范围在工程阶段明确。

第一阶段面向自己的实际使用：几十件到数百件重要物品，以电脑、手机、摄影器材、耳机、家电等为主。大额商品购买低频，可能几个月只有几笔；不愿逐笔记生活流水；重视视觉质量、快速录入和多年后的回顾价值。

实物部分的核心场景是购买时打开、维修时补记、出售时结算、偶尔回顾。当前版本另已支持第 17 节的低频财富盘点、重要支出、周期费用与虚拟资产；以及总览中的综合回顾（D）。专业金融管理不因这些扩展自动纳入范围。

产品回答四个问题：

1. **现在拥有什么**：物品、分类、数量及活跃、退役、售出状态。
2. **为重要物品花了多少钱**：当前持有物的购入金额、历史购买总额、期间与分类支出。
3. **持有多久、成本如何**：持有天数、维护投入、售出回收及日均成本。
4. **这些年发生过什么**：心愿、购买、维护、保障、退役和售出的个人时间轴。

日均成本只是成本观察指标，不代表使用频率、满意度或真实市场价值。

## 2. 范围与产品原则

### 2.1 范围

| 当前实物版核心 | 当前实物版排除 | 将来按真实需求评估 |
|---|---|---|
| 实物资产、分类、购买信息、图片 | 股票、基金、债券、金融账户、金融净资产 | 虚拟资产、软件授权、订阅 |
| 生命周期、保修、维护、出售 | 日常收入支出、餐饮流水、信用卡账单、复式记账 | OCR、条码、设备型号识别 |
| 心愿转资产、时间轴、统计 | 银行/微信/支付宝同步、在线估值依赖 | 可选同步、二手估值、自然语言查询 |
| 本地存储、导出、备份恢复 | 云账户、多用户协作、部署 Web Server、Docker | Windows 等其他平台 |

房租和订阅虽然在早期讨论出现过，也不属于当前实物 MVP。AppleCare 等与物品直接相关的延保可作为 Warranty 记录，不由此扩展成订阅系统。

### 2.2 原则

- **Local-first**：核心能力离线可用，无需注册；数据保存在本机 SQLite 和文件系统。
- **无需常驻**：双击应用即可使用；完整退出后不留下项目自建服务或守护进程。关闭窗口与退出应用的行为应明确。
- **Desktop-first**：侧栏、表格、详情面板、键盘操作，充分利用 Mac 屏幕；不直接放大手机界面。
- **低录入成本**：新增资产一屏完成基本信息，更多字段渐进展开。
- **数据可带走**：可读导出与完整备份分别服务分析和恢复，附件也必须纳入恢复。
- **完成度优先**：先做好资产详情、快速新增、时间轴、统计和备份。

视觉方向参考原讨论中的 Wealthfolio、Linear、Raycast、Arc 和 Apple 应用：安静、清晰、信息密度适中。它们是体验参考，不构成功能或代码复用承诺。

## 3. 信息架构与桌面交互

```text
Overview 总览
Assets 资产
  All / Active / Retired / Sold
Wishlist 心愿
Timeline 时间轴
Insights 统计
Settings 设置
```

采用左侧导航 + 主内容区；列表单击可打开右侧详情面板，双击进入完整详情。返回后保留筛选、排序和滚动位置。浅色、深色、跟随系统属于基础体验。

### 3.1 Overview

顶部显示当前持有物购入金额、当前持有数量、平均持有时间、进行中心愿数；活跃数量单独标明。避免将 `Active` 数量误标为全部持有数量。

中部展示累计购入金额趋势、按购入金额的分类分布；分类图建议圆环配列表。趋势描述的是历史购入累计金额，不是市场估值曲线。底部展示最近 5–8 个事件，点击进入关联物品或心愿。

### 3.2 Assets

- Grid 用于看图片和回顾；卡片展示封面、名称、品牌、购买金额、状态、持有时长。
- List 用于比较与检索；列包括名称、分类、购入日期、购入金额、状态、持有时长，可按列排序。
- 支持按生命周期、分类、保障状态筛选，按名称等搜索；标签筛选随 P1 标签功能提供。
- 第一屏新增字段：名称必填，分类、价格、购买日期、封面可填。更多详情折叠展示品牌、型号、渠道、序列号、保修、备注。
- 未知购买价格或日期允许留空，界面明确显示未知，不自动写成零。新增资产表单预填本地今天；用户可改选实际购入日期，也可清空表示未知。编辑已有资产保留原日期，不补写今天。

详情页包括封面与名称、品牌分类、编辑与生命周期操作、购买资料、持有与成本、保障、维护、附件及单件时间轴。重要信息应在同一详情中看全，不为每条资料增加跳转。

2026-09-29 用户确认详情排布：顶部为封面｜名称与操作｜成本卡（单位成本、持有天数与目标进度），窄于 1120px 时成本卡移到标题下方；左栏为「购买与投入」两栏网格（购入日期、渠道、购入金额、维护投入、总投入、序列号，按次加持有时长、售出加净成本；品牌型号只在标题下显示），其后为备注、售出记录、保障、维护、图片；右栏只放单件时间轴。没有记录的保障、维护、图片收成一行，右侧直接给添加按钮。

### 3.3 搜索与快捷键

2026-09-29 用户确认统一顶栏与页面内搜索方案，并指定交给 zcode 实现；完整规则及验收见下方第 3.5 节（U12）。基础物品搜索继续覆盖名称、品牌、型号、分类、备注和序列号，加入标签；本次补齐其他模块的页面内搜索。全局搜索与命令面板仍是后续范围，不能把当前页输入框只改文案就当成跨模块搜索。

| 快捷键 | 意图 |
|---|---|
| ⌘N | 当前页新增；账户页新增账户，综合页打开新增菜单；无新增入口页不触发 |
| ⌘F | 聚焦当前页搜索；无搜索入口页不切页、不触发物品搜索 |
| ⌘, | 设置 |
| ⌘E | 编辑选中物品，沿用既有作用域 |
| ⌘K（后续） | 全局搜索与命令面板，不属于 U12 |

模态框、提交中与未决回执优先，不能借快捷键穿透到后台新增。中文输入法组合期间不处理 Esc；普通输入框内不劫持编辑键。搜索框聚焦时 Esc 清空搜索，菜单内 Esc 关闭菜单并返回触发按钮；表单内 Esc 沿用关闭规则，不同时清空后台搜索。

### 3.5 U12 · 页面顶栏与搜索统一（2026-09-29，已确认，随 1.13.0 发布）

**决策来源：** 用户指出财富模块仍显示“新增资产”不合适，要求一并统一其他细节与搜索；对页面相关操作、当前页搜索方案回复“感觉是可以的”，指定准备设计文档和分阶段交接给 zcode。本节取代旧的全局固定“新增资产”入口约定，不改变各领域保存、金额、删除恢复及样例规则。历史记录中的“新增资产”属于旧界面用语。

#### 3.5.1 页面矩阵

顶栏左侧保持当前面包屑，右侧为当前页搜索和操作。具体模块直接打开已有表单；综合页通过菜单选择。页面内部不再保留重复的顶部搜索/主按钮，空状态可保留同一动作的引导。

| 账户与盘点 | 搜索账户 | 开始盘点 / 新增账户；无可盘点账户时新增账户为主 | 新增账户 |

| 周期费用 | 搜索计划 | 新增计划 | 新增计划 |
| 虚拟资产 | 搜索虚拟资产 | 新增虚拟资产 | 新增虚拟资产 |

“新增资产”在面向用户的实物新增按钮、表单标题、提示和帮助文案统一为“新增物品”；不要批量重命名底层 Asset 类型、命令或历史验证记录。

新增记录菜单按固定顺序列出：新增物品、新增心愿、新增账户、记一笔支出、新增计划、新增虚拟资产；只显示已开启模块。选择后进入对应模块并调用已有新增流程，取消停留于目标模块，保留原综合页的筛选以便返回；不增加新式表单。菜单不加入需要指定对象的付款、维护、退款；开始盘点仍在账户页执行。

账户搜索只过滤账户列表，不缩小盘点范围；在账户页非账户列表标签中输入搜索时切到该页账户列表，并有可见标签状态，不跨模块跳转。无可盘点账户的判断使用全部有效账户，不受搜索结果影响；加载中或失败不能误判成首次空库。

#### 3.5.2 搜索语义与匹配字段

下列细则是已确认方向的实施约束。统一采用去除首尾空白、英文不区分大小写的字面子串匹配；空字符串等于未搜索。各字段之间为 OR；不支持拼音、模糊纠错、正则或全文索引。输入上限 200 字符，中文、空格、引号、百分号和下划线均按普通文本处理；后端查询参数化，不把通配字符当匹配表达式。

| 页面 | 必须匹配的已有文本字段 |
|---|---|
| 物品 | 名称、品牌、型号、分类、标签、备注、序列号；不得缩减已有可搜字段 |
| 账户 | 名称、类型显示名、已有备注 |
| 支出 | 列表记录标题、分类显示名、已有独立支出备注、来源对象名称；覆盖自动汇入及独立记录 |
| 周期计划 | 名称、分类显示名、已有备注 |
| 虚拟资产 | 名称、类型显示名、提供方、已有备注 |
| 心愿 | 名称、已有品牌/型号/分类/备注；保留既有搜索覆盖 |
| 时间轴 | 事件标题、事件类型显示名、来源对象名称及已展示说明；不为搜索读取所有附件或档案私密字段 |
| 素材 | 名称、分类、已有搜索别名，复用现有逻辑 |
| 最近删除 | 各类删除项显示名称、类型显示名及已有父对象名称；不递归扫描被删附件 |

字段不存在时不新增持久字段；U12a 核对字段映射并记录实际接口。搜索对当前状态、年份、领域、类型等筛选取交集，保留现有排序。改变关键词或筛选重置分页；必须先搜索后分页，不能只过滤当前已加载一页。只有接口确实返回完整集合时才能在前端过滤；分组日期、日期待补、结果数和加载更多须同步正确。关键字不改变年份/分类等筛选选项的可用集合。

**统计边界：** 搜索只影响结果列表与“找到 N 条”，不影响年度支出、净资产、周期负担或页面既有汇总卡片。汇总可以继续响应原有业务筛选，不能响应新增关键词；需分离列表查询与汇总查询。此规则也适用于物品页面，若旧实现让摘要随关键词变化，必须拆开并验证。结果计数为全部匹配条数，不冒充当前页行数。

无结果显示“当前条件下没有找到记录”，提供“清除搜索”；有附加筛选时另提供“重置筛选”（清除关键词并恢复页面默认筛选，不强行改成全部年份）。底层库为空时显示原首次引导，加载错误显示重试，不把错误或加载态伪装成无结果。删除恢复后的结果数、分页和空态重新计算。

#### 3.5.3 状态、快捷键和数据保护

- 搜索词以页面为单位保存在应用内存，切页恢复、重启清空；同一物品模块的不同状态列表共享物品搜索，状态筛选独立。不要新增 localStorage/sessionStorage 搜索历史。
- 切换样例/我的资料、恢复备份、重置资料或 generation 改变时，清空关键词、结果缓存、旧请求和返回上下文，防止跨库复用；普通同库刷新保留搜索。
- 快速输入 A→B、清空、切页、切库时只接受当前请求结果，错误同样不得晚返回覆盖新结果。输入法组合期间不提交半成品查询；需要防抖时仍处理取消与请求身份。
- 来源跳转按稳定 ID 打开，即使对象不匹配目标页面搜索或不在当前页；返回时恢复出发页关键词、筛选、页码及数据就绪后的滚动位置。不得为打开来源永久覆盖用户搜索词。
- 顶栏与页面表单共用同一动作及禁用条件，不通过模拟 DOM 点击触发。当前模块自身就绪决定可用性，不再依赖物品页加载成功；资料切换、提交中、未决回执等全局保护继续有效。
- 样例中新增物品依 D14 切回我的资料；其他新增沿用各自现行资料归属，不能统一成全部切真实库，也不能扩大样例禁止范围。普通关闭不保存草稿，提交结果未知须核对。
- 原生菜单中的 ⌘N、⌘F 项文字随当前页显示实际动作，无对应动作时置灰（2026-09-29 用户要求「把原生菜单文字也改成随当前页变化」）。
- 关闭模块时关闭其菜单/待触发动作并清理该模块搜索状态；任何隐藏入口或快捷键都不能绕过模块开关。重新启用时数据仍在。
- 新菜单具备可访问名称、方向键/Enter/Esc/Tab 操作与焦点恢复；关闭表单后焦点回到仍存在的触发按钮，否则回到当前页标题。

## 4. 资产与生命周期

### 4.1 资产资料

| 分组 | 字段与要求 |
|---|---|
| 识别 | 名称、品牌、型号、单一分类、封面；序列号可选 |
| 购买 | 实付购入价、币种、购入日期、购买渠道 |
| 扩展购买信息 | 订单号、发票号、卖家、购买链接、原价与折扣；不是 P0 必填 |
| 生命周期 | 当前状态、退役日期、售出日期与售价 |
| 其他 | 多标签（P1）、备注、创建/修改时间 |

已确认首版一条资产表示一件可独立维护、退役或售出的物品，不做数量库存或组合拆分。两台同型号设备分别记录；成套且整体处置的物品可作为一件。

不要同时以 `purchase_price` 和 `actual_price` 存储两份含义相同的实付价格。原价与折扣为扩展资料，统计以实付价为准。

### 4.2 状态独立于保障

| 状态 | 含义 | 是否仍持有 |
|---|---|---|
| Active 活跃 | 仍在主要使用 | 是 |
| Retired 退役 | 不再主要使用，但仍拥有 | 是 |
| Sold 售出 | 已完成出售 | 否 |

P0 支持 Active → Retired、Active → Sold、Retired → Sold。流程保留 Retired → Active 重新启用并记录事件；状态动作按时间顺序，冲突由用户更正源记录，不自动重写历史。2026-09-28 用户确认不增设 Returned / Lost / Gifted 等处置状态（见 D17 规则 1）：扔掉、丢失、赠送记为退役，退货直接删除。

保修独立显示，资产可同时为 Active + Covered。退役不是删除，售出不是删除；二者都保留历史购买与维护信息。

### 4.3 售出

标记售出时输入日期和实际售价，平台、买家及备注为选填。保存时更新资产、记录售出事件、刷新当前持有统计和净成本，整体成功或整体失败。销售日期不能早于购入日期；待售物品不能提前按已售处理。

出售数据录错时应通过更正业务记录同步修正时间轴和统计，不能靠另加一条无关联事件修补。已确认允许撤销误记售出，恢复到该次售出前的 Active 或 Retired 状态；清除当前有效售出结算，并同步统计与时间轴。真实售出后又购回则另建资产，原资产保留真实处置历史；退货作为后续状态扩展，不纳入 P0。

## 5. Warranty 与 Maintenance

### 5.1 Warranty

一件资产可有厂家保修、延保、AppleCare、商店保修或其他保障。记录类型、提供方、起止日期和备注，可关联附件。

保障状态自动计算：未记录保障、保障中、即将到期、已到期。已确认截止日当天仍有效、30 天内到期提示「即将到期」；未来才生效或缺失日期应单独说明，不能误算成当前已覆盖。多份保障分别展示，摘要以当前有效保障判断。

P1 评估在到期前 30/7/1 天提醒。设计意图是由系统调度本地通知，不要求应用常驻；所选桌面技术栈能否在退出后可靠投递、如何更新/取消计划、权限拒绝后的降级均待真实打包验证。P0 在应用内展示保障状态即可。

### 5.2 Maintenance

记录日期、类型、标题、描述、金额、币种、服务商和附件。已确认维护日期可未知，已知费用仍计入总成本，但不伪造期间归属；售出后可补录持有期间的历史维护。类型包括维修、保养、清洁、部件更换、升级、其他。例如相机清洁 ¥300，既应出现在维护列表，也应出现在时间轴中。

同一笔成本只记录一次：升级如果作为维护类型保存，生命周期成本不能再加一次 `upgrade_cost`。金额未知应与零费用区分。P0 支持维护新增、编辑、软删除、从统一最近删除恢复及对应统计更新；保障误删同样可恢复。P1 补充 PDF 等附件。

## 6. 成本与统计口径

本节统一各页面的术语。人民币范围、持有成本、自然日边界和缺失值等核心规则已经用户确认，决策记录见第 15.2 节。

### 6.1 指标定义

| 指标 | 范围 / 计算 |
|---|---|
| 当前持有数量 | 未删除的 Active + Retired |
| 活跃数量 | 未删除的 Active |
| 当前持有物购入金额 | 当前持有物的已知实付购入价合计 |
| 历史购入金额 | 所有未删除资产的已知购入价，包括已售出与退役 |
| 期间购入金额 | 购买日期位于期间内的购入价合计 |
| 累计购入趋势 | 按购买日期累计，出售不回减；不是当前持有价值 |
| 总投入 | 购入价 + 已记录维护费用（含升级） |
| 净生命周期成本 | 总投入 − 实际售出回收金额 |
| 日均持有成本 | 总投入 ÷ 持有天数 |
| 售出后净日均成本 | 净生命周期成本 ÷ 截至售出日的持有天数 |
| 售出保值率（P1） | 售价 ÷ 购入价；购入价为零或未知时不计算 |

「资产价值」默认指历史购入金额，不是二手估值或金融净资产。时间轴金额是展示信息，不与业务表重复累加。

### 6.2 日期与退役

已确认采用自然日口径：

```text
截止日 = 已售出 ? 售出日期 : 今天
持有天数 = max(1, 截止日与购买日期的自然日差 + 1)
```

购买当天按 1 天，避免除零；未来购买进入心愿，历史资产不能使用未来购入日期。售出后天数固定。Retired 仍持有，因此「日均持有成本」继续摊薄；若以后增加「活跃使用成本」，需记录活跃区间，不能把两者混称为使用成本。

购买日期未知时不展示持有天数或日均成本；购买金额未知时成本标为不完整，汇总同时展示未计入数量。不得以零代替缺失数据，让不完整统计看起来完整。

### 6.3 金额与币种

用户已确认：P0 只使用人民币（CNY），资产、维护、售价及心愿预计价格均使用人民币，首版不提供币种切换、汇率输入或自动换汇。currency 字段可为未来迁移保留，但其存在不意味着界面已支持多币种；多币种功能以后另行设计。

金额使用最小货币单位整数或精确定点方案；展示时再舍入。购入、维护、售价通常非负，零购入价可用于赠品。售出所得大于总投入时可出现负净成本，应如实显示并说明，不强行截断为零。

例：购入 ¥16,999，维护 ¥300，售价 ¥5,000，持有 1,000 天，总投入 ¥17,299，净成本 ¥12,299，毛日均 ¥17.30，净日均 ¥12.30。

2026-09-29 用户确认设置与操作入口修订：分类图标是分类列表的小标识，新建区域收起为“分类图标＋当前图形”，展开选择，不影响默认物品封面。售出渠道与标签补齐改名、删除：改名同步关联记录；删除显示引用数量（含最近删除），可替换为其他同类选项或清空；只移除选项关联，不删除物品或售出记录。停用继续保留历史关联。修改需事务化、重复请求安全，并使受影响物品的旧编辑版本失效。

设置采用固定两列：左列选项管理、样例体验；右列功能模块、资料管理，各列自然排列，窄窗单列，不做自动换列排序。详情返回采用 36px 高浅底按钮，保留筛选和列表位置。应用内关闭叉统一左上、36×36px 点击区、16–18px 图形，边距约 16–20px；标题说明不影响按钮位置，长表单顶部操作固定。普通关闭仍直接丢弃未提交输入；未知结果回执规则不变。系统原生窗口按钮不改。

约束与一致性要求：

- 打开 SQLite 外键约束；重要写操作使用事务；评估 WAL 与备份方案。

- Wishlist 转换应有唯一约束或幂等键，防止重复资产。
- 文件写入不能假装被 SQLite 事务自动回滚：使用临时文件、提交后移动和失败清理，并避免删除共享附件。
- 迁移前备份，记录 schema 版本，升级失败不能留下半迁移状态。数据库版本、应用版本、备份格式版本分开管理。

- **CSV 导入（P1）**：已由 [D21](#d21--导入资产表2026-09-29-用户确认u14) 细化为「只新增」导入：模板列按名称识别，预览有效/无效行和原因，确认后整批提交。

### 12.2 完整备份（P0）

```text
Possio-backup-<date>.zip
  manifest.json
  database.sqlite
  attachments/
```

清单包括备份格式版本、应用/schema 版本、创建时间和校验信息。备份应获得一致的数据库快照并覆盖附件，不能在 WAL 存在时简单复制一个可能不完整的主库文件。

恢复先检查版本、完整性、路径和关联，再写入临时目录；保留当前数据的恢复前备份，全部通过后切换。失败不得破坏原数据。P0 以完整替换恢复为目标，合并恢复不默认纳入。

2026-09-29 起自动备份以 [D20](#d20--默认自动备份2026-09-29-用户确认u13) 为准（默认开启、有改动才备份、保留 7 份、不提醒）；下段为早期 P1 设想。P1 可在启动时检查距离上次成功备份是否超过 7 天，并按可配置保留策略备份；应用退出时备份仅作为补充，不能作为唯一可靠路径。自动备份无需常驻服务。备份和附件也属于用户私密资料；加密备份属于后续评估项。

### 12.3 删除与恢复

2026-09-28 起以 [D17](#d17--删除与恢复的统一规则2026-09-28-用户确认) 为删除与恢复的统一规则，覆盖全部模块；本段为 P0 时的范围记录。已确认：P0 使用软删除，统一“最近删除”管理资产、维护、保障三类记录，支持按类型筛选及恢复；删除期间排除相关常规统计，首版不自动永久清空。P1 再完善批量清理、保留策略和永久清除确认（D17 定为手动永久删除、不自动清空）。恢复资产恢复其原本有效的关联档案，不自动恢复此前独立删除的维护/保障；父资产已删除时，恢复子记录先引导恢复父资产。删除操作不得破坏共享附件。删除不等于售出或退役。

## 13. 技术方向与边界

原讨论推荐 Tauri 2 + React + TypeScript + Rust + SQLite，作为后续工程设计起点；UI 候选为 Tailwind CSS、Radix/shadcn，图表在 ECharts 与 Recharts 中择一。本文不锁定依赖版本或给出未经验证的 API 用法。

```text
React UI
   │ Tauri Command / IPC
   ▼
Rust Application / Service
   ├─ Repository → SQLite
   └─ Storage → Local File System
```

React 不直接写 SQLite。Rust 应用层统一做输入校验、生命周期动作、成本计算和事务边界；前端管理交互状态和展示。核心计算可独立验证，不能由每个页面复制一套公式。

发布形态目标为内嵌前端资源的桌面 App，不运行额外 Express/HTTP API 服务。开发用前端服务器不等于发布时必须启动服务器，验收以打包应用为准。选用 Tauri 本身也不会自动保证启动速度、包体或零残留进程，必须实测。

原稿建议目录按功能组织前端，后端分 commands、services、repositories、models、migrations、storage。此处仅保留组织原则，不在文档整理阶段创建空代码目录或确定完整工程结构。

### 15.1 关键验收场景

1. 离线打开打包应用，新增资产，退出后重新打开仍存在；无项目自建后台服务残留。

#### D17 · 删除与恢复的统一规则（2026-09-28 用户确认）

决策来源：用户询问删除物品后时间轴、心愿等是否应一并隐藏，并要求只从产品本身判断“最近删除”是否有必要；竞品核验见[竞品调研 4.11](COMPETITOR_RESEARCH.md#411-删除与恢复2026-09-28-专题核验)。用户确认以下逻辑成立，先写入产品设计；本条替代 12.3、F07 中与之不一致的表述。用户随后要求全部实现（U10）。

**为什么保留：** 删除后需要找回的场景有两类：当场误点，以及删错对象（如重复录入时删掉了带照片、维护的那条），后者常在数天或数周后才发现。物志低频打开、纯本地、没有云端历史，整库备份恢复会覆盖之后的全部录入，无法找回单条；一条物品又带着照片、票据、维护与心愿来历，难以重建。因此保留软删除与“最近删除”。“本来就不该有”的记录无需恢复，但与上述情况在删除时无法区分，统一进入最近删除。

**规则：**

1. **含义唯一。** 删除表示“这条记录不该存在”（误录、重复、试录），不用于表达物品已离开。确认框提示：不再使用请用退役或售出。**不增设额外处置状态**（用户确认，避免状态复杂度）：扔掉、丢失、赠送都记为**退役**；退货视为这次购买不成立，直接**删除**。
2. **带走附属，不碰独立对象。** 附属记录离开主体没有意义，随主体一起删除：维护、保障、生命周期动作、售出、周期付款、关联到物品的支出及其退款、附图。独立对象照常显示，只在关联处提示“关联的××已删除，可恢复”：心愿、账户、未关联的支出、周期计划。心愿实现后生成的物品被删除时，心愿仍为已实现，时间轴保留“心愿已实现”，只隐藏该物品的购入。
3. **所有界面一致消失。** 删除后不出现在列表、搜索、时间轴、统计、总额与预计总额、页面内提示和系统通知中；完整备份保留，可读导出（CSV）不包含。
4. **恢复即撤回那一次删除。** 该次删除带走的内容原样回到各界面，保留原 ID、状态与关联；此前已单独删除的子记录保持删除；恢复子记录时父对象已删除，先引导恢复父对象；恢复时引用的分类等已不存在则归为未分类，不阻断恢复。恢复不重复生成事件、付款或图片。
5. **一个“最近删除”。** 所有可删除对象（含心愿）进入同一列表，按删除时间排列，注明该次删除带走的内容（如“含 3 条维护、5 张图片”），可按类型筛选、逐条恢复。永久删除与清空须二次确认，永久删除时才清理不再被引用的图片文件。**不自动清空**：低频使用下定期清空可能在用户发现误删前就已清除；最多提示占用空间。
6. **即时撤销。** 删除成功后短暂显示“已删除 · 撤销”，覆盖当场误点，不必进入最近删除。

**实现状态（2026-09-28，U10）：** 以上规则已在开发分支实现，差额（已删物品的关联退款、时间轴“心愿已实现”、心愿删除、即时撤销、删除确认的退役引导、“带走内容”说明、永久删除与清空）均已补齐；结果与未验边界见 [U10 记录](verification/U10_DELETION_RESULT.md)。

#### D18 · 编辑资料与完整档案的职责划分（2026-09-28 用户确认）

决策来源：用户指出“编辑资料”与“完整档案”中删除、维护、保障、退役、售出等入口职责交叉，要求按正常理解统一；用户确认以下划分，先写入产品设计；随后要求全部实现（U10）。

**原则：编辑资料管“这件物品是什么”，完整档案管“它经历了什么”；每条记录的修改与删除都在它自己的表单里。**

| 界面 | 职责 | 包含 | 不包含 |
|---|---|---|---|
| 物品摘要（列表侧栏） | 快速查看 | 关键信息；“打开完整档案”“编辑资料”入口 | 任何修改操作 |
| 编辑资料 | 物品本身的属性 | 名称、分类、价格、购入日期、渠道、品牌型号、备注、图片、图标、标签、成本方式；底部“删除物品” | 状态、维护、保障、售出 |
| 完整档案 | 查看全部并记录发生的事 | 新增维护、添加保障、退役/重新启用、售出；时间轴与各类档案 | 删除物品 |

删除物品只放在编辑资料：按 D17，删除表示记录录错、不该存在，与改名、改价同属纠正录入；放在完整档案易被理解为“物品离开就删除”。

**退役与售出是事件，不是属性。** 它们有日期、改变状态、影响成本并进入时间轴，只在完整档案操作，不进入编辑资料。按钮随状态变化：在用显示“退役”“售出”；已退役显示“重新启用”“售出”；已售出不显示状态按钮，只保留售出记录的修改入口。

**区分“真的反向发生”与“当初记错”：**

| | 真的发生 | 当初记错 |
|---|---|---|
| 退役 / 重新启用 | “重新启用”或再次“退役”：新增事件，历史保留 | “撤销误记”：删除这条事件，如同未发生 |
| 售出 | 卖出后又买回：另建新物品（D07） | “撤销误记售出”：回到售出前状态 |

撤销误记只作用于该物品**最近一条**生命周期事件（含售出）：要撤销更早的事件，须先撤销其后的事件，避免历史出现无法解释的前后状态。撤销后状态、持有天数与成本按剩余事件重新计算。

**每条记录在自己的表单里修改和删除：**

| 记录 | 入口 | 表单内 |
|---|---|---|
| 物品 | 编辑资料 | 修改属性；底部删除物品 |
| 维护、保障 | 点击该记录 | 修改内容；底部删除 |
| 售出 | 售出记录的“修改” | 修改日期、售价等；底部“撤销误记售出” |
| 退役、重新启用 | 时间轴该事件的“更正” | 修改日期；底部“撤销误记”（仅最近一条） |

**1. 选择方式（沿用 Mac 习惯）**

**2. 批量面板**

**3. 批量表的共同规则**

- 接近全屏的大窗口，一行一件：物品 | 当前值 | 新值（及该操作的其他列）。标题写明“为 N 件物品分别设置……”，保存按钮写明“保存 M 项更改”。
- 每行默认“保持不变”或开关关闭，改动才计入更改；表头“全部设为”一次填满整列，个别行再单独改。统一值与逐件不同都在同一张表完成。
- 不适用的行灰显并写明原因（如“已售出 · 不能退役”），不参与保存。校验按行就地提示，规则与单件操作完全相同（D11 日期顺序、D18 状态按钮），不另立规则。
- 保存为一次提交：全部生效或全部不生效；成功后显示撤销条（及 ⌘Z），一次撤回整批。撤回时某件已被其他操作改过，则跳过该件并说明，不覆盖后来的修改。
- 控件复用现有组件：日期用“选日期”日历 + 键盘输入（不照搬手机滚轮），分类、渠道、标签用现有下拉选择；图标、颜色和样式沿用现有 tokens。任何新图形（如盾牌插图）须先出同尺寸对照并经确认。
- 样例中可用，改动只留在样例。只作用于物品；心愿、支出、账户暂不批量。

**4. 各操作的表格**

| 操作 | 批次 | 列与默认值 | 适用范围 |
|---|---|---|---|
| 分类与渠道 | 第一批 | 当前分类 → 新分类；当前渠道 → 新渠道；默认保持不变 | 全部选中物品（含已售出，分类是属性） |
| 状态标签 | 第一批 | 当前标签 → 新标签（可设为“未设置”） | 全部选中物品 |
| 退役 | 第一批 | 当前状态 · 开关“退役” · 退役日期（默认今天） | 使用中；日期不早于购入与上一条状态记录、不晚于今天 |
| 重新启用 | 第一批 | 开关“重新启用” · 日期（默认今天） | 选中的全部为已退役时，退役表换为此表 |
| 统计口径 | 第一批 | 不计入总价 / 日均 / 统计 / 时间轴四个勾选框，表头可整列勾选或取消 | 全部选中物品 |
| 删除 | 第一批 | 无表格；确认后按 D17 进入最近删除，每件一条，可分别恢复 | 全部选中物品 |
| 添加保障 | 第二批 | 开关“添加保障” · 类型（默认厂家保修）· 开始日期（默认**购入日期**，未知时今天）· 结束日期（默认开始后一年）· 状态预览（如“保障中 · 还剩 364 天”与细进度条，沿用现有保障状态样式） | 与单件添加保障相同的限制；已售出行默认关闭 |

**5. 不做的操作**（相对有数、持物）：批量置顶（置顶本为挑少数，单件已有）、复制（属于单件“复制为新物品”，与 D06 同型号分别建档相关，另行评估）、分享与保存图片（社交场景，非本地档案所需）、导出所选备份（完整备份为整库恢复，局部备份会使恢复规则复杂；需要时另评估“导出所选为 CSV”）。

**界面对照稿（设计阶段，已确认并实现）：** 同尺寸（1280×820）浅/深色对照见 `docs/ui/batch/`：现状 `before-*`、选中 3 件与批量面板 `panel-*`、批量分类表 `category-*`、批量退役表 `retire-*`。由 [对照脚本](ui/batch-mock.js) 在浏览器预览真实页面上生成，只改临时 DOM，新增样式均以 `batch-` 开头并使用现有 tokens。

**6. 验收样例（虚构；实现结果见 U11 记录）**

#### D20 · 默认自动备份（2026-09-29 用户确认，U13）

决策来源：用户询问还有哪些值得做，Claude 建议先补备份；用户认为物志隔一二十天才打开一次，提醒应来自系统之外，随后在讨论中确认：**默认开启自动备份，不主动提醒、不让用户先选位置；高级用户可在设置中另加备份位置；退出不能变慢**。系统通知（“很久没打开”提醒）不在本批：资料只在打开 App 时变化，不打开就没有未备份的新内容。iCloud 同步不在本批，iCloud 云盘只作为“额外备份位置”可选的普通文件夹。

**为什么默认放在资料目录旁：** macOS 的 `~/Library/Application Support/<身份>/` 相当于 Windows 的 AppData，把 App 拖进废纸篓不会删除它，重装后资料与备份仍在。它防误删误改后回到几天前、恢复出错与数据库损坏；不防硬盘损坏或丢失 Mac（Time Machine 用户会顺带备份此目录，其他人可设额外位置）。

**规则：**

1. **默认开启、无提示。** 新装与升级后直接生效，不弹窗、不要求选位置。设置中可关闭；关闭后不再生成，已有备份保留。
2. **只在有改动时备份。** 我的资料在本次运行中有任何写入后，空闲 2 分钟在后台生成备份；没有改动不生成。样例中的改动、空资料库（含最近删除在内都没有记录）不备份。**例外（2026-09-29 用户确认，1.14.1）：**我的资料已有记录、但还没有任何自动备份（从旧版本升级，或备份被手动删光）时，启动后约 30 秒直接备份一次，不等改动。
3. **退出不等待。** 不在退出时备份。退出时若备份正在进行，直接退出；未完成的临时文件不会成为备份，下次启动约 30 秒后补做。
4. **每天一份，保留 7 份。** 同一天多次备份覆盖当天那一份；按日期保留最近 7 份（按有改动的日子计），更早的自动删除。只删除自动备份自己的文件。
5. **格式与手动备份相同。** 仍是完整备份（`.possio`），可用现有“从备份恢复…”选择，也可在自动备份列表中直接恢复；恢复沿用检查、确认替换与保护副本流程。
6. **失败不影响资料。** 失败时保留此前备份，设置中显示原因与时间，约 30 分钟后或有新改动后再试；不弹窗打断。
7. **额外备份位置（高级，默认关闭）。** 设置中可选任意文件夹（如 iCloud 云盘、外接盘）；之后每次自动备份成功后复制一份过去，同样保留 7 份、只删除自己的文件。位置不可用（外接盘未连接等）只记录错误，不影响主备份；可随时取消。
8. **设置中可见。** 显示开关、上次自动备份时间、份数与占用空间、“打开备份文件夹”、每份的日期与大小及“恢复”；额外位置的路径、上次复制结果与更改/取消。

**已知上限：** 每份都是完整备份，照片多时占用随之增长（约为资料大小 × 7）；备份进行时其他读写短暂排队，资料较大时可能有数秒等待。占用明显过大时再改为照片去重存储。

**实现状态：** 已随 1.14.0 发布，首次备份例外随 1.14.1 发布，验收见 [U13 记录](verification/U13_AUTO_BACKUP_RESULT.md)。

**U13 验收：** ①新装默认开启、无提示；②改动后空闲 2 分钟生成当天备份，同日再改覆盖当天，无改动不生成；③样例改动与空库不备份；④备份中退出不留坏文件，重启后补做；⑤只保留 7 份且不删其他文件；⑥失败保留旧备份并在设置中说明，之后重试；⑦设置显示状态、占用和列表，可打开文件夹、从某份恢复；⑧关闭后不再生成、已有保留；⑨额外位置复制、保留、位置不可用与取消；⑩删除 App 后重装，自动备份仍在并可恢复；⑪浅深色同尺寸对照与隔离原生验证。

#### D21 · 导入资产表（2026-09-29 用户确认，U14）

决策来源：用户问「有了导出资产表，还需不需要导入资产表」；Claude 建议只做首次搬入用的「只新增」导入，不做导出→修改→导回的更新；用户回复「那就按照你的意见来」。

**用途：** 把已有表格（Excel、Numbers 或其他 App 导出）一次搬进物志。回改更新、整库迁移与恢复由完整备份负责，不走 CSV。

**规则：**

1. **只新增，不覆盖。** 每个有效行新建一件物品；不按档案编号或名称更新、合并已有物品。
2. **模板与列。** 设置 › 资料管理可「下载模板」：名称、分类、品牌、型号、购入价（元）、币种、购入日期、渠道、状态、退役日期、售出日期、售价（元）、备注。按列名识别、顺序不限；多余列（含导出表的「档案编号」）忽略。导出表可直接导入。
3. **格式。** UTF-8（可带 BOM）、逗号分隔；只有名称必填。价格为元，最多两位小数，可带 ¥ 与千位逗号；日期 `YYYY-MM-DD` 或 `YYYY/M/D`；币种留空或 CNY/人民币。状态留空视为使用中；已退役须填退役日期；已售出须填售出日期与售价。日期不得晚于今天、不得早于购入日期。
4. **先预览，后写入。** 选择文件后只检查不写入：显示可导入件数、每个无效行的行号与原因、将新建的分类与渠道、疑似重复。确认后才写入；文件在预览后被改动则要求重新选择。
5. **疑似重复。** 与现有未删除物品名称、购入日期、购入价都相同的行标为疑似重复，默认跳过，可勾选一并导入；文件内相同的行视为多件，不标记。
6. **整批成功或整批不写。** 全部有效行在一个事务中写入，任何失败都回滚，资料保持原样；无效行不导入，也不阻止其他行。重复提交同一次导入不会重复新增。
7. **分类与渠道。** 按名称（不区分大小写）匹配现有项，未知名称新建并排在末尾，分类图标为箱子。
8. **样例不可导入**，与样例不接受新增资产一致。上限 5,000 行、5 MB。
9. **不包括：** 图片、维护、保障、心愿、标签、账户与其他模块。

**U14 验收：** ①模板可下载且能被导入（空模板导入提示无有效行）；②导出表原样导入到另一资料库，件数、分类、渠道、状态、售出与退役日期一致；③无效行逐行说明原因、不阻止有效行；④未知分类/渠道在预览中列出并在导入后出现；⑤疑似重复默认跳过、勾选后导入；⑥写入失败整批回滚；⑦预览后文件被改动时拒绝写入；⑧样例中入口不可用。

## 16. 核心用户流程（交互草案）

状态：2026-09-24 已依据 D01–D12 细化；输入和失败结果见功能规格，像素与实际交互验收仍待实现后验证。此处规定用户路径及页面状态，不等于已经做出 UI，也不锁定组件、像素或工程实现。业务语义沿用前文，具体字段不在这里另建一份清单。

### 16.1 所有流程共用的交互规则

- 用户操作在成功保存前不改变已保存档案或汇总。保存中防止重复提交；失败保留输入并提供重试。
- 输入合法性在对应字段附近说明，不用笼统的“操作失败”代替可修正原因；金额统一显示人民币。
- 2026-09-27 用户修订：点叉、返回或取消直接关闭，普通未保存输入不持久化、不弹草稿确认。保存固定在顶部；已发出且结果未知的请求保留用于核对，不按普通输入丢弃。
- 错误同时区分用户可修正的问题和存储失败，不向普通界面暴露 SQL、IPC 或文件系统堆栈。
- 完成操作后保持对象可见，并更新相关统计；从列表打开的详情应尽量保留筛选与滚动上下文。
- 失效、被删除、未找到和加载失败不是同一种空状态，分别提供恢复、返回或重试入口。

### F01：第一次使用与新增资产

**用户目标：** 快速记录一件重要物品，即使尚不清楚全部购买资料。

入口：首次打开总览的“添加第一件资产”、Assets 的“新增资产”、⌘N。

1. 初次进入无需登录，也不强制完成分类设置或观看引导。首件真实资产前默认展示明确标识的独立 Demo 样例库，八件虚构物品可用于体验浏览、详情、回顾和编辑；“新增资产”进入正式资料库的统一新增表单。取消首件录入返回样例，成功保存后自动退出样例。正式资料库始终保留自己的空状态与新增入口。
2. 打开统一新增表单。名称必填；分类、购买金额、日期和图片按需填写，品牌、渠道、序列号等在“更多资料”展开。
3. 新增资产的购入日期预填本地今天，可用鼠标选日期或用键盘输入；不确定实际购入日期时可清空，已有资产编辑时不覆盖原日期。其他日期字段也提供鼠标日历与键盘输入。未知金额仍保留为空。已有分类可选择，暂不分类也可保存。
4. 默认从素材库选择示意图并预览，也可通过次要入口导入自有图片；无法读取或格式不支持时说明原因，允许移除图片继续保存。用户选择保留的图片必须成功保存，不能静默丢弃。
5. 保存成功后进入该资产详情，状态为 Active；出现建档信息，只有已知购买日期才显示对应购买事件。

**成功检查：** 新记录只产生一次；图片托管后原文件被移动仍可读取；回到列表能找到它。重新打开应用后记录仍存在。

**取消/失败：** 取消不留下半条资产；名称为空不能提交；日期在未来提示使用心愿；存储失败保留表单和已选图片供重试。

### F02：查找、查看与更正资产

**用户目标：** 找到物品，核对资料并修正补录信息。

入口：Assets 列表/网格、总览最近事件、Timeline 关联对象。

1. 通过名称或基础资料搜索，并可按分类、生命周期或保障状态筛选。
2. 列表选择资产打开详情面板；进入完整详情可查看成本、保障、维护和时间轴。详情中的“编辑”或 ⌘E 进入更正表单；删除物品位于更正表单底部，界面分工见 [D18](#d18--编辑资料与完整档案的职责划分2026-09-28-用户确认)。
3. 补填未知日期/价格，或修正名称、渠道等资料；保存后原记录更新，不新增另一件资产。
4. 涉及购买日期和费用的更正同步成本与有效事件。归档状态操作通过明确动作入口完成，不能在普通字段编辑里无提示变成另一种状态。

**成功检查：** 列表、详情和统计使用一致的资料；更正购买日期不会把建档时间改成旧日期。返回列表保留筛选，若更正后不再匹配筛选则说明原因。

**取消/失败：** 输入未保存时原资料保持不变；无搜索结果提供清除筛选；误删对象从链接进入时提供“前往最近删除”，而不是显示数据库错误。

### F03：记录维护与保障

**用户目标：** 在同一物品档案中补记维修投入和保障资料。

入口：资产详情中的“记录维护”“添加保障”；两类记录使用独立表单和成本语义。

1. 维护表单填写发生日期、类型、标题、费用和服务商等；费用可为零或未知。升级是一种维护，不能在另一处再累计同一笔费用。
2. 保存后维护列表和时间轴显示同一次业务记录；成本立即依据完整性和金额更新。维护费用未知时说明成本不完整。
3. 保障表单填写类型、提供方与日期，可连续添加多份。保存后详情分别展示，并更新有效保障摘要；保障变化不改变 Active/Retired/Sold。
4. 点击维护/保障记录打开其表单更正，删除位于该表单底部（D18）；相关有效事件和统计同步变化，删除前说明影响。

**成功检查：** ¥200 的维护只增加 ¥200 总投入；多份保障不会变成多个生命周期状态；保障过期不会把资产自动退役。

**取消/失败：** 日期矛盾就地提示；保存失败不出现虚假的新记录。P0 不以通知权限、PDF 上传或常驻服务作为前提。

### F04：心愿新建、实现与转资产

**用户目标：** 保留购买前的想法，买到后自然接入资产档案。

入口：Wishlist 的“新增心愿”；进行中心愿详情中的“已购入”。手动实现及攒钱达到目标会直接建立关联资产，保留心愿记录。

1. 新建心愿时填名称，按需补充价格、分类、渠道、实现方式、备注与附图；加入日期默认本地今天。保存时依第 7 节规则确定实现状态。
2. 当前只提供未实现与已实现，不再提供放弃入口；旧放弃记录仍作为历史保留。
3. 选择“已购入”后打开资产确认表单，沿用名称、分类和图片，填写实际价格/日期等。预计价格仅作参考，不能静默当成实际价格。
4. 确认后一次完成资产创建、心愿实现和关联事件，跳转新资产详情，提供返回原心愿的入口。
5. 已转换的心愿显示关联资产，不再提供第二次转换按钮；关联资产被软删除时引导恢复，不能默认再次转换。

**成功检查：** 心愿原始预计价和加入日期保留；实际购买金额只计一次；资产能回溯到原心愿。

**取消/失败：** 取消确认表单时心愿保持原状态；任一步保存失败不得留下半转换；连续点击只创建一件资产。

### F05：退役与重新启用

**用户目标：** 记录暂时不再使用，仍保留拥有关系。

入口：Active 资产的“标记退役”；Retired 资产的“重新启用”。

1. 选择退役日期，可补备注，界面说明“仍计入持有，日均持有成本继续计算”。
2. 保存后状态为 Retired，活跃数量减少，持有数量不变；时间轴增加退役事件。
3. 重新使用时选择“重新启用”，填写日期，状态回到 Active，并新增对应事件；不清掉之前的退役历史。
4. 误点或误记时，从时间轴该事件的“更正”表单选择“撤销误记”，删除这条事件而非追加反向事件；只能撤销最近一条生命周期事件（D18）。

**成功检查：** 重新启用不会重置购买日期、持有天数或维护成本。Sold 不能直接点“重新启用”，必须区分误记售出和真实购回。

**取消/失败：** 取消或失败保留原状态；日期不能早于购买或前一有效生命周期动作（资料已知时）。补录复杂倒序历史的处理留到 Spec 明确，不自动改写后续历史。

### F06：售出、修改与撤销误记

**用户目标：** 保存真实处置结果，同时允许更正录入错误。

入口：Active/Retired 资产详情的“售出”；Sold 详情售出记录的“修改”，“撤销误记售出”位于修改表单底部（D18）。

1. 填写售出日期与实际售价，平台、买家和备注选填；展示已知总投入与结算预览。出售金额是必填的实际数字，可为零但不能以空值冒充零。
2. 确认后资产进入 Sold，退出当前持有统计；持有天数固定到售出日，展示净生命周期成本及净日均持有成本。
3. 仅金额或日期写错时修改原售出记录，保持同一出售事实；保存后更正有效时间轴和结算。
4. 整次出售误记时选择撤销，预览将恢复的状态。确认后回到该次售出前的状态，撤掉当前有效结算和有效售出事件，保留必要更正记录供内部追溯。
5. 实际卖出后又买回时，从“新增资产”记录新购入；原 Sold 档案继续保留，不复用撤销入口改写真实历史。

**成功检查：** 从 Retired 售出再撤销应回到 Retired；撤销后天数重新计算到今天；出售收入不直接写入任何金融账户。

**取消/失败：** 日期不合法时阻止提交；取消不改变状态；结算资料不完整时明确标注，不展示虚假的精确净成本。

### F07：统一最近删除与恢复

**用户目标：** 去除误录资料，同时可以找回误删档案。

业务规则以 [D17](#d17--删除与恢复的统一规则2026-09-28-用户确认) 为准：删除范围扩展到心愿与各扩展模块，并补充处置引导、即时撤销、“带走内容”说明与手动永久删除；下列步骤为 P0 已实现部分，与 D17 不一致处按 D17 调整。

入口：“编辑资料”表单底部的删除物品，维护/保障表单底部的删除（D18）；Settings 中的“最近删除”。

1. 删除确认说明资产将移入最近删除，关联记录一起隐藏且退出常规统计；这不代表退役或出售。
2. 删除资产成功回到原列表；删除单条维护/保障后留在所属资产详情。两者都提供前往最近删除的入口。常规搜索与 Timeline 不继续展示已删除资产的有效业务记录。
3. 最近删除统一列出资产、维护、保障，可按类型筛选；显示名称、类型、所属物品、适用的原状态和删除时间，可选择恢复；首版不自动永久清空。
4. 恢复时保留原 ID、原生命周期和资料，恢复此前有效的关联档案；独立删除的维护/保障仍保持删除。子记录的父资产若已删除，先引导恢复父资产；心愿转换关系继续指向同一资产。

**成功检查：** 恢复一件 Sold 资产后仍为 Sold，不重新算入当前持有；恢复不重复创建时间轴事件、维护或图片。共享文件与其他资产不受影响。

**取消/失败：** 删除取消不改变资料；恢复失败保留最近删除项和已有文件，展示重试。仅关闭通知式提示不等于永久失去恢复机会。

### F08：导出备份、CSV 与恢复

**用户目标：** 带走数据，并能在需要时完整恢复。

入口：Settings 的“数据与备份”，明确分开“完整备份”“CSV 导出”“从备份恢复”。

1. 完整备份选择目标文件位置，说明包含资产、关联记录和托管图片；生成并验证完成后才提示成功与保存位置。
2. CSV 导出明确仅为可读资产表，不包含完整附件和全部关联历史，不用它替代备份。
3. 恢复时先选择备份并检查格式、版本和完整性；展示备份时间、记录概况及“替换当前资料”的影响。
4. 用户确认后先保护当前数据，再恢复；成功后重新加载总览和列表，并报告结果。
5. 完整备份应保留软删除记录及其附件，保证恢复后“最近删除”仍可用。缓存可重建，不属于用户档案。

**成功检查：** 在全新数据目录恢复后，关联资料与图片可读，金额/状态一致；恢复不会把已售出或已删除资产变成活跃。

**取消/失败：** 取消选文件不产生任务；恢复前校验失败不动现有数据；恢复中失败保留可用的原数据与备份；不能只因为 ZIP 文件存在就提示完整成功。

### 17.3 X01 · 账户与负债档案

**使用场景：** 建立需要定期核对的平台清单，知道资金分布以及还欠多少。

- 账户字段：名称、平台、资产或负债方向、分类、币种、是否计入金融净资产、启用/停用日期、备注。无需真实完整卡号、登录信息或平台凭据。
- 候选资产分类：现金与存款、投资账户、基金、债券、公积金、其他。信用卡欠款、贷款等作为负债；公积金可纳入净资产，但不能标成可随时使用的现金。
- 股票/基金/债券首批允许按账户总值记录；一个混合证券账户标为“混合投资”，不根据名称猜测股票或债券占比。
- 平台只是分组，不额外产生可累加金额。一个证券账户若已包含现金和持仓总值，不再另加同一持仓；未来支持拆分时必须在“总值计入”和“组成项计入”间明确选择。
- 建议资产余额和负债欠款均输入非负金额，由方向决定加减；负债输入区清楚写“尚欠金额”。负余额/信用卡溢缴款另行定义，不用双重负号解决。
- 住房、车辆等贷款可逐个账户标记“不计入金融净资产”（已确认，见 17.12）；默认计入，标记变化按纳入范围变化处理并提示跨期不可直接比较。
- 每次盘点新增观测记录，不覆盖旧月份。一次盘点只有一个日期，所有条目视为该日观测，账户不单独存观测日期（已确认，见 17.12）；“确认未变”即在该盘点日重新观测。账户最新值显示所属盘点日期。
- 停用账户保留历史；若仍有非零余额/欠款，提示处理余额，不能直接让它从下一期净资产消失。误建删除与真实销户分开处理；历史更正须列明受影响盘点。

### 17.4 X02 · 集中盘点与历史快照

**核心流程：** 选择盘点日期 → 集中查看各账户上次值 → 对照平台逐行填写或确认未变 → 检查缺漏与本次合计 → 一次保存。

建议规则：

1. 默认今天，可补录过去的实际盘点日；月度只是推荐频率，同月多次或数月一次都允许。不给未盘点月份补造真实数据，也不保存未来实际余额。
2. 每行展示前次金额、前次日期、本次金额、差额及确认状态。旧值可作参照，不能未确认就当作本次新观测；“确认未变”是明确动作。
3. 金额未知与零分开；可明确保存“不完整盘点”，但须显示缺失账户和已知小计，不进入完整净资产的增长率比较；曲线上建议以空心点等区别于完整点，比较时跳过。后来补齐后重新核对。
4. 完整性按该日期应纳入的账户清单检查；事后补建一个早已存在的账户时，提示哪些历史快照可能漏项，不静默补零。更改纳入范围也应提示跨期不可直接比较。
5. 保存以一整次盘点为单位成功或失败；重复点击只产生一次。建议同一自然日保留一份有效盘点，更正在原盘点上进行（A 首版改前预览影响、不留修订日志，X-D01）；另一个日期才新增时间点。
6. 保存名称/类别/纳入规则及所用余额、汇率的历史语义，日后改名或重新分类不应无提示重写过去图表。更正历史金额须先预览受影响期数并统一重算该期相关展示；完整修订追溯不在 A 首版（X-D01）。
7. 普通未提交表单仍按既有规则关闭即丢弃，不引入自动草稿或退出确认；保存失败保留当前输入，结果未知则核对原请求，不能重新造一份快照。
8. 可选盘点提醒只负责提示，绝不在无人核对时自动保存金额；应用无需常驻。

### 17.5 X03 · 金融净资产、结构与变化

首页明确分开以下指标，避免统一成含义不明的“总资产”：

| 指标 | 建议口径 |
|---|---|
| 金融资产 | 同次盘点中，纳入范围且去重后的资产账户金额合计 |
| 负债 | 同次盘点中尚欠金额合计，以正数展示 |
| 金融净资产 | 金融资产 − 负债，允许为负 |
| 持有物购入金额 | 沿用现有实物统计口径，不加入金融净资产 |
| 已记录重要支出 | 指定期间已记录、去重的实际支出；不是全部生活消费 |
| 固定支出年化负担 | 当前有效周期计划折算值；不是当年实际已支付 |

财富页提供净资产/资产/负债曲线、账户明细、资产分类分布及两个盘点日期的比较。默认显示实际观测点；缺月不插入零，不把跨三个月的变化标成“本月增长”。只有一个点时展示该期结构，不制造趋势。

`净资产变化 = 本次净资产 − 上次可比净资产`。前次净资产大于零且两期完整、纳入范围可比时，可显示变化率；前次为零或负数时仅展示金额变化。余额增长包含存入、支出、转移、估值与汇率等影响，不能直接叫“投资收益率”。无流水数据时不能自动归因为工资、投资收益或消费。

正向资产分类占比的分母为金融资产合计，负债另列；资产合计为零时不画比例圆环。投资账户未拆分时只显示账户级结构，不伪造证券级配置。

**币种：** 第一批仅人民币（已确认，见 17.12）；确需外币时再允许原币金额＋该次盘点的手工汇率，约定为“1 单位原币折合多少 CNY”。保存历史汇率，不能用今日汇率重写历史；缺汇率标为不完整，不按 1:1 或零折算。多币种为待确认范围。

**实物估值建议：** 普通实物和虚拟服务默认不计金融净资产。原聊天中的投资性房产、黄金、收藏品及估值历史列为后续选项；若启用，应与金融净资产分开展示“含选定实物估值的净资产”，保存估值日期和来源，并防止与账户中的同一资产重复计入。购入价不自动等于当前估值。

### 17.6 X04 · 重要支出与实物联动

以下保留初始需求语境；首版采用 X-D05–X-D08：购入/维护自动计入，沿用物品排除统计开关，不新增纳入标记。当前实现口径见 ADR-001 第 18 节。

**使用场景：** 买电脑只记一次，也能单独记录旅行、培训等没有对应实物的支出；回顾重要消费，而不承担每日记账。

- 独立支出字段：名称、日期、实际金额、分类、备注、可选附件和关联对象。可记录退款，必须关联原支出并使用实际退款日期；购入事实与退款事实分开保留。
- “重要”建议由用户选择，不设强制 ¥1,000 阈值。资产/维护表单提供是否纳入重要支出的标记；新记录默认值待确认，旧资产不批量改写。
- 对已有实物购入、维护、售出及未来周期支付，金额和日期来自唯一源业务记录。重要支出页只保存关联或展示投影，不复制一份可独立修改的金额。更正源记录后各页同步更新。
- 一次性虚拟资产购买也可关联；已有独立支出后补建对应物品，应支持关联原记录，预览并消除重复项。
- 售出回收单独列出，不当成第二笔负支出或抹掉历史购入；退款净额与售出回收分别显示。不同性质的回收不能混称投资收益。
- 已知金额但日期未知的记录进入“日期待补”小计，不分配到某个月；未知金额显示未计入数量。单独支出建议日期和金额必填，源资产仍保持原有可空语义。
- 同一笔支出可以在重要支出页和周期支出页出现，但综合支出合计按源记录去重。时间轴中购买及其支出标签合为一次业务事件。
- 买卖、维护和支付记录均不自动增减账户余额：净资产由用户核对的快照得出。支出用于解释背景，不宣称完整还原两次快照之间的变化。

### 17.7 X05 · 固定周期支出与续费

以下含后续增强建议；首版采用 X-D09–X-D12：所有已确认付款自动进入重要支出，不保存计划版本，仅页面内提示。计划版本、系统通知不属于已交付能力。

**使用场景：** 看清房租、软件订阅、服务、保险等周期负担，知道下次何时付、哪些仍在持续。

- 计划字段：名称、分类、每期金额、币种、周期（每 N 月/年）、起始日、下次付款日、结束日、续费方式、提醒和备注；可选关联虚拟资产或保障记录，房租可独立存在。
- 状态区分生效、暂停、已取消/已结束。取消自动续费并不等于当前服务立即失效；服务有效期在虚拟资产中独立展示。
- 首批建议先覆盖月付、季付、年付；按量、按使用时长及不规则扣费另行设计。实际支付金额可以不同于计划。
- 修改价格、周期或取消日期应从指定日期生效，保留此前计划版本及已确认支付，不回写旧月份。
- “下次应付”是计划；只有用户明确确认日期和实际金额后才是“已支付”。到期、提醒触发和打开应用都不能自动创造真实付款。重复确认同一期不生成重复支付；允许补录多期。
- 支付记录唯一；若同时标记为重要支出，在 X04 通过关联展示。计划金额、年化数字和支付记录不能三次相加。
- 月付年化 = 每期金额 × 12；季付年化 = × 4；年付月均 = ÷ 12。统一币种后汇总、最后舍入。已暂停/取消的计划不进入“当前持续负担”。
- “未来 12 个月预计支付”按实际到期表计算，与年化分开展示；有截止日期或涨价时两者可以不同。月末起算按月历处理，例如 1 月 31 日 → 2 月末 → 3 月 31 日，不逐月永久漂移到 28 日。
- 本地提醒可复用现有能力，但编辑、取消、暂停后必须重排；权限拒绝不阻止保存计划。退出后的新类型通知仍需隔离原生验收，不能借既有提醒结果直接宣布通过。

### 17.8 X06 · 虚拟资产档案

以下含长期需求；首版范围以 X-D13–X-D16 及 ADR-001 第 21 节为准，未实现凭证附件、虚拟日均成本或虚拟心愿。即将到期的已实现规则为手填有效期 30 天、关联周期计划 7 天；D 沿用该规则，不把第 17.12 节早期概述中的 30 天扩展到所有关联订阅。

**使用场景：** 记录已购买的软件授权、域名和服务订阅，查看有效期、费用、平台及历史。

- 字段：名称、类型、提供方、购买日期、开通日期、有效期或永久有效、购买/管理链接、备注、凭证；关联一次性购买或周期计划。
- 买断授权、有限期权益和周期订阅分开表达；不强行套用实物的退役、售出、保修状态。首批建议仅支持有效、到期、停用等必要状态，具体定义待评审。
- 一个服务档案可以关联一份当前周期计划和历史版本，档案与计划不重复存相同费用。域名有效期、自动续费设置、实际付款是三件事。
- 虚拟资产成本只能累计已确认支付；未来续费计划不算已花费。日均成本需另定起止日、退款和有效区间后再实现，不直接复用实物持有天数。
- AppleCare 继续保留在现有保障域，需要周期费用时关联同一保障，不再创建一份重复保障。账号密码、完整密钥托管不纳入首批档案能力。
- 实物心愿转换保持现状；未来支持虚拟心愿时，应明确对象类型及转换规则，不能把每个达标心愿都自动生成实物。

### 17.9 X07 · 综合展示与 X08 · 数据保护

**综合展示建议：** D 的具体页面与统计方案统一见第 17.13 节。最近完整盘点、持有物购入金额、已记录重要支出和当前固定负担分别展示。时间轴汇集已发生事实；虚拟资产到期与待付款放入「待关注」，不伪装成付款或购买事件。更正回到源记录，不建立第二套金额事实。

新增财富、支出与虚拟档案需要可发现的入口，但本节不冻结新的导航结构。现有实物左侧状态导航及页面分区保持原基线；进入 UI 设计后再提交整体入口方案和同尺寸对照，新增界面复用 SVG、tokens 与组件。批量盘点应支持键盘逐行录入、就地错误提示和大屏可读表格，不能以通用后台 CRUD 表替代核心流程。

**数据保护要求：** 账户、快照、历史规则、支出、周期计划、实际支付、虚拟档案、关联及附件都进入同一完整备份范围；快照和支出增加可读导出。引入/导出与完整恢复的含义仍须区分。

旧版备份向新版恢复时保留全部实物事实，新模块初始为空，不推算过去余额。新版备份交给不支持其格式的旧版必须明确拒绝。删除/恢复要保持跨模块关联，停用不等于删除；更正或删除快照前预览受影响趋势，确认后恢复时不得重复产生事件。

正式资料库继续禁止用于开发、测试和验收。迁移、失败恢复、旧备份兼容与通知验证只在开发预览或隔离身份的虚构库进行；本次不创建迁移、不启动正式 App、不读取真实账户数据。金融信息显示遮罩、加密备份及本地存储加密可独立评估，不把简单遮罩称为加密。

#### 17.13.3 统计口径（继承规则与展示建议）

下列计算继承 A–C2 的已实现口径（ADR-001 第 17–21 节）；D 新增的是展示组合。实现时必须复用同一统计来源，不在前端另算一套。

| 展示 | 数据与时间口径 | 缺失与比较规则 |
|---|---|---|
| 金融净资产 | 最近一份完整、有效盘点中纳入的金融资产减负债；显示盘点日期与距今天数 | 无完整盘点显示“尚无完整盘点”；有更新的不完整盘点时提示其日期/缺漏，不以已知小计覆盖完整值 |
| 较上次可比盘点 | 沿用财富页的可比性判断和绝对变化；百分比仅在前期净资产 > 0 时显示 | 显示两个真实日期；不可比时说明原因，不称投资收益或本月收益；单点不生成走势 |
| 当前持有物 | 沿用实物总览的纳入范围、持有数量和已知购入金额 | 明确为购入金额；未知金额另计件数，不与金融净资产相加，也不因年份选择回算历史持有 |
| 已记录重要支出 | 沿用重要支出页同期间的支出、退款、净支出和售出回收；净支出 = 支出 − 退款，售出回收单列 | 日期待补、金额未知分别提示；已关联说明不重复计费；售出回收不再从净支出扣一次 |
| 固定负担 | 沿用周期费用页今天的月均与年化；可跳转查看未来 12 个月预计 | 未确认付款、计划金额和年化值不加入实际支出；暂停/结束计划沿用原排除规则 |

金融净资产曲线只用真实完整盘点点位；不完整盘点标日期与缺漏，不画成零或已知小计；不补造没有盘点的月份。D 首批不将支出柱图与净资产线图叠在一起，不以净资产变化减去支出推算收入或收益。

支出去重按来源记录身份：实物购入/维护、独立未关联支出、已确认周期付款、未关联计划的虚拟购买各计一次。关联周期计划的虚拟资产只通过付款计费；独立支出关联物品后其说明不再累计，退款仍沿用原退款规则。金额更正、排除、软删除、恢复后，综合页和领域页必须得到同样的结果；快照余额不随这些操作自动增减。

#### 17.13.4 待关注与时间轴

**待关注（新展示建议）：** 先列最新不完整盘点，再列已到期待确认付款/已到期权益，最后列即将到期事项；同类按日期、稳定 ID 排序。无事项时显示安静的空态，不制造“今日任务”。盘点只显示距上次天数，不先设“每月必须盘点”的逾期规则。金额未知等完整性说明留在所属卡片。

- 周期费用沿用“已到期待确认”和未来 7 天提示；虚拟资产使用原状态规则（手填 30 天、关联计划 7 天，停用不提示）。不新增 macOS 通知或后台任务。
- 同一计划与其关联虚拟资产的到期事项合并成一组，保留“付款待确认／权益到期”各自的日期和含义；组内分别提供进入计划与虚拟档案的入口。不是同一关联关系的事项不凭名称合并。显示“待关注事项组”，避免误作账单数。
- 提示点击只定位已有页面/记录；实际支付仍由原付款表单明确确认。打开综合页、到期或点提示都不能自动生成付款。

**时间轴（新能力与补齐建议）：** 在现有时间轴增添「全部／实物／心愿／财富盘点／支出」领域筛选，并兼容既有事件类型筛选。虚拟购买与周期付款均归支出；虚拟到期只放待关注，不同时伪造购买或支付事件。

- 新增盘点事件：每份有效盘点按其盘点日投影一次；完整时展示净资产，不完整时展示缺漏，点击打开该份历史盘点。更正同一份盘点不额外产生一笔支出或重复事件。
- 保留现有购买、维护、保障、生命周期、心愿、独立支出、退款、付款与虚拟购买事件；补齐付款/虚拟档案的定位跳转。一个事件即使有两个相关对象，也只展示一次。
- 日期未知事件沿用现有处理，不塞到今天；未来到期留待关注。综合页近期记录按所选年展示最新 8 条事实，空态写明所选期间无记录，不擅自切换年份。
- 来源已删除或在跳转前失效时刷新并说明；不得误跳同名记录、创建替代记录或显示过期金额。返回时恢复原筛选和滚动位置。
